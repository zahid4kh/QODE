# Window, settings, themes and the rest

## MainWindow

`MainWindow` (src/window) is the composition root: it owns `ProjectManager`, `ProjectExplorer`, `EditorManager`, and `Terminal`, laid out in a horizontal splitter (left panel | `m_workSplit` | right-hand island; `m_workSplit` puts the agent (`m_agentIsland`, the main view, toggled by `m_aiAct` / `setAgentVisible`) left of the editor column (`m_vsplit`, `setEditorColumnVisible`, View > Editor Panel Ctrl+Alt+E): the column opens with the first file and closes with the last, a column closed by hand (`m_editorHiddenByUser`) is not reopened by files the agent opens, one of the two is always shown, and `agentVisible` / `editorVisible` / `editorWidth` are part of the project layout; QODE starts with the chat closed (the editor column's welcome page with the recent projects), and `m_launching` keeps it closed while `openInitialPaths` restores the last project, whose saved `agentVisible` only applies when a project is opened later; the left panel is `SideSections`, collapsible Explorer / Version Control / Search / Tasks sections whose expanded state persists in `SettingsManager::sideSections`; open one with `m_side->setExpanded(i, true)`; the whole panel hides via `m_explorerAct` = Toggle Sidebar, Ctrl+B / toolbar, with its visibility and width persisted). The terminal sits below `m_workSplit` in the vertical splitter `m_vsplit`, so it spans the agent and the editor column (or whichever of them is shown) and never opens the editor column on its own; the right-hand island keeps the full height. It wires their signals together, owns all menu/toolbar `QAction`s, and persists/restores window state and session through `SettingsManager`. Edit actions are routed to whichever widget has focus (`forwardToFocus`).

`MainWindow`'s member functions are spread over files by area: `MainWindow.cpp` (constructor and wiring, session and layout, projects, the run / terminal flow, palette, quick open, bookmarks), `MainWindowUi.cpp` (actions, menus, toolbar, status bar), `MainWindowLsp.cpp` (LSP menu and status, server installs, Go to Definition, code actions, workspace edits, rename, references, colour swatches), `MainWindowGit.cpp` (git actions, status, gutters, diffs), `MainWindowPanels.cpp` (Python / Expo / Spring strips, the right-hand island's previews and Gradle panel), plus the feature files (`MainWindowAssist`, `Cpp`, `Debug`, `Http`, `Ide`, `Inline`, `Jvm`, `JvmEdit`, `Ktor`, `Maven`). New code goes into the file of its area, or a new `MainWindow<Area>.cpp`, rather than `MainWindow.cpp`.

The View menu is kept short enough to fit a laptop screen (it used to spill into a second column): the palette, sidebar / terminal, the main panels (chat, Claude Code, editor, game) and the preview / bookmarks / TODO lists stay at the top level; everything else is grouped in submenus: **Tool Panels** (HTTP Client, MCP Servers, Python Packages, Gradle, Maven, Spring Boot, Ktor and their dialogs; project-specific ones stay hidden), **Editor** (splits, word wrap, guides, sticky scroll, minimap, breadcrumbs, Folding), **Code Insight** (edit predictions, semantic highlighting, symbol highlights, light bulb, code lenses, Inlay Hints) and **Appearance** (Theme, zoom, hidden files). Run File / Run Configuration are only in the Run menu. Shortcuts of actions in nested submenus still work (Qt resolves a menu action's window through its parent menus), and the command palette flattens submenus (`collectActions`), so new options go into the matching submenu, not the top level.

## startup

`app/StartupProfile` times the start: `begin()` first thing in `main()`, named `mark()`s through `main()` and the `MainWindow` constructor (each charges the time since the previous one), and `finish()` once the window has painted for the first time (`finishOnFirstPaint`: an app-wide event filter watching for the first `Paint` of a widget in the window, then a zero timer so the flush is included; the window itself gets no paint event, its children cover it). The time before `main()` (loading Qt's libraries) comes from the process start time in `/proc/self/stat`, about 10 ms precise. Help > Startup Time shows the report (Copy button); `QODE_STARTUP_PROFILE=1` also prints it to stderr, plus a `QODE later:` line for every panel created afterwards. A panel created on first use times itself with a `StartupProfile::Later` scope and is listed under "Created when first used", marked "(during startup)" when it ran before the first frame (its time is then in a startup row too). Put new marks where a new block of the constructor costs time; keep them to a few rows (one per area, not per function).

Measured in Xephyr on the development machine, no project: about 410 ms from `main()` to the first frame before this work, about 185 ms after. What went:

- **The right-hand island's panels are created when first used.** `mediaPanel()`, `markdownPreview()`, `springPanel()`, `webPreview()` (MainWindowPanels.cpp), `httpPanel()`, `ktorPanel()`, `mavenPanel()`, `debugPanel()` create the panel, add it to `m_rightStack`, wire it, and hand it the state it would have been given so far (project root, Maven build folder, the `.http` document, preview targets, breakpoints). The members stay null until then, so code that only *updates* a panel checks for null (`if (m_maven) m_maven->setBuildDir(dir)`), code that *shows or uses* one calls the getter, and "is it showing" is `rightPanelShows(m_x)` (false for null; an empty stack's `currentWidget()` is null too, so a plain comparison would match). `showInRightPanel(panel)` ends a Markdown / SVG preview and opens the island on a panel; `clearPreviews()` stops a video and drops the rendered Markdown. A new right-hand panel follows the same pattern. When each is created: media and Markdown preview with the first image / video / preview; HTTP with the first request, panel, or tooltip in a `.http` file; Maven and the web preview when first shown; the debug panel when shown or when a debug session starts (`launchDebug`; its "Stop on uncaught exceptions" box is not saved, so a missing panel means its default, on); the Spring Boot and Ktor panels as soon as the project is a Spring Boot / Ktor project (`updateSpringUi` / `updateKtorUi`), because they collect the server's log from the start whether shown or not, and in other projects never. The Gradle panel is still created with the window (4 ms): its Build tab follows every Gradle build started in the terminal and takes the terminal's compiler errors, shown or not.
- **Island pages must not ask for width.** `m_rightStack` is a `QStackedWidget`: its minimum width is the largest of *all* its pages, hidden ones included, and a non-maximized main window grows to fit it when any panel opens (Linux and Windows alike). A one-line `QLabel` without word wrap asks for its full text width: show paths / URLs in such panels with `window/ElidedLabel` (`setFullText`, elided in the middle, full text in the tooltip). Found 2026-11-08: the Gradle panel's folder label made every right panel widen the window by ~350 px. Check with `xprop -id <window> WM_NORMAL_HINTS` (program specified minimum size). Also: a label matched by an app style sheet rule (`QLabel#emptyText`) gets its contents margins reset by the style sheet; give it padding in a style sheet instead of `setContentsMargins`.
- **The video player is created with the first video** (`MediaPanel::ensurePlayer`). `QMediaPlayer` loads the FFmpeg backend, about 90 ms (it logs "Using Qt multimedia with FFmpeg"); images and SVG previews never need it.
- **The Claude Code view is created when first shown** (`AiHub::claudeCode()`), about 12 ms; `AiHub` keeps the editors, project root, git-dirty flag and file list for it until then. It is created at startup when it was the page shown last (`SettingsManager::chatPage`).
- **The window is built top-down.** A widget moved under a new parent has its style (the app style sheet), font and palette resolved again over its whole subtree, so the old order (panel, then its `Island`, then splitter, splitter, central widget) paid that once per level, about 50 ms. The constructor now creates the splitters and empty islands first, inside the window (`setCentralWidget` first), and puts each panel straight into its island (`Island(nullptr)` + `Island::setContent`). Keep new layout code in that order.

What is left is mostly fixed cost: about 65 ms of Qt's own `QApplication` setup (platform plugin, display connection; the bundled fonts and the theme are under 5 ms of it), about 30 ms for explorer, git, search, tasks and the editors, about 15 ms for the actions and about 10 ms for the QODE chat.

## settings

`SettingsManager` (QSettings wrapper for global prefs, window state, recent projects → `~/.config/QODE-AGENTIC/QODE.conf`) and `Theme` (dark/light palettes). Per-project data (theme, tab size / spaces / format-on-save / venv-activation overrides under `settings`, run commands, open files/active file, bookmarks) is a JSON document at `~/.config/QODE-AGENTIC/projects/<name>-<hash>.json`, loaded by `SettingsManager::setProject` from `MainWindow::onProjectOpened`/`onProjectClosed`; the same accessors (`theme`, `runCommand`, `bookmarks`, `openFiles`…) read/write it while a project is open and an unsaved in-memory copy otherwise. The project's window layout (sidebar/terminal visibility and sizes, section states, editor split tree) is the `layout` object (`SettingsManager::projectLayout`), written by `MainWindow::saveSession` via `currentLayout()` and applied after the files reopen by `applyLayout()` + `EditorManager::restoreLayout`; a project with no saved layout keeps the window as it is. Nothing is written inside project folders.

## themes

`Theme` is a struct of named colours (`Theme::fields()` is the table behind JSON and the editor: key, label, group, member ref; includes the 16 ANSI colours, status colours and find-match colour). `ThemeManager` (singleton) holds the built-in `dark`/`light`/`darcula` (`Theme::darcula_()`) and the greyscale `mono-dark`/`mono-light` (`Theme::monoDark_()`/`monoLight_()`; the light one is a mid silver, not white) plus user themes loaded from `<config>/themes/*.json` (`{name, base, colors{key: "#rrggbb"}}`; missing keys fall back to the base theme; file watcher reloads on external edits). A theme id (file stem) is what `SettingsManager::theme()` stores, globally or per project. `Theme::byName(id)` resolves through the manager, so every widget keeps calling `Theme::byName(SettingsManager::instance().theme())`; a change is announced by `SettingsManager::refreshTheme()` → `themeChanged`, and caches keyed on the theme name must also compare `ThemeManager::revision()` (see `FileIcons`). While the theme editor (`dialogs/ThemeEditorDialog`, View > Appearance > Theme > Edit Themes…) is open, `setPreview` makes `byName` return the working copy for any id, so the whole window follows edits live; Save writes the JSON and activates it, built-ins save as a copy. Never hard-code a colour in a widget: add a field to `Theme`.

## fonts/icons

all `.ttf` files in `resources/fonts` (Plus Jakarta Sans = UI, JetBrains Mono = editor/terminal, all weights) are embedded in `qode.qrc` and registered in `Application`; new font files must be listed in the qrc. Since Qt 6.11, setting the app style sheet refills Qt's per-widget-class fonts (QLabel, QMenuBar, …) with the desktop font from the platform theme, which turned every label and menu into Ubuntu Sans. `Application::applyTheme` and `applyZoom` therefore set the app font again *after* the style sheet. Doing it later (on `ThemeChange`) left the first frames in the desktop font. Icons are Lucide SVGs in `resources/new-icons` (the app logo lives in `resources/icons`: `qode-source.png` is the original artwork, `qode-<size>.png` are its cropped rounded-corner renders used for the window icon and installed into hicolor); `settings/Icons` recolours the single-colour SVGs for the active theme, and `explorer/FileIcons` maps file names to tinted file-type/folder icons (used by the explorer via `ProjectModel::data`, tabs, Quick Open and search results). Kotlin files carry the Kotlin logo (`kotlin.svg`, a filled shape drawn a little smaller than the line icons), scripts (`*.kts` but not `*.gradle.kts`) the logo with a terminal badge on a `panel`-coloured disc (`makeKotlin`, composed per size), and Gradle build scripts (`*.gradle`, `*.gradle.kts`) Gradle's logo. JetBrains' brand guidelines require the notice "Copyright © 2026 JetBrains s.r.o. Kotlin and the Kotlin logo are trademarks of JetBrains s.r.o." wherever the Kotlin logo ships or shows: Help > About QODE (with Ktor's), the status bar's Kotlin button tooltip, a comment in `kotlin.svg` and `packaging/copyright`. They must stay. `BranchButton`/`BranchPopup` are the branch switcher (Version Control toolbar and status bar).

## zoom

`SettingsManager::uiZoom` (50–400 %, per project; status-bar `ZoomPopup`, Ctrl+= / Ctrl+- / Ctrl+0, Ctrl+wheel in the editor) zooms the whole app. Two places apply it, and they must never both scale the same value:

- **Sources already at the current zoom:** the application font (`Application`: 9.5 pt × zoom), `SettingsManager::editorFont()` (base size × zoom) and `SettingsManager::scaled(px)`.
- **`Application::scaleWidget`** scales what widgets set from plain numbers: style sheet `px`/`pt`, minimum/maximum sizes, icon sizes and layout margins/spacing. It does this on first polish, on a style sheet change and in `applyZoom`.

Every font a widget sets is derived from one of those sources, so it is already zoomed. `scaleWidget` therefore leaves a new widget's font alone. On a zoom change, `applyZoom` multiplies each explicit font by new zoom / old zoom, and owners that reapply `editorFont()` on `editorSettingsChanged` (`CodeEditor::applySettings`, …) then set the exact value. The editor once scaled explicit fonts on polish as well, so an editor opened at 130 % got 130 % × 130 % = 169 %, while the same zoom set live looked right.

A widget that sets its own fixed size from zoomed numbers (`scaled()`, or zoomed font metrics) sets the property `qodeZoomed`, so `scaleWidget` skips its minimum/maximum size. It must then resize itself on `editorSettingsChanged` (see `WelcomePage::fitRecent`). QTabBar's close buttons (class `CloseButton`) get their size from the theme style sheet (`QTabBar CloseButton { min-width … }`), which is already zoomed, so `Application` marks them `qodeZoomed` on polish. Left to the style's pixel metric they stayed 20 px at every zoom, and the button sat flush against the tab's right edge (the tab's padding does not apply to it; the `margin-right` on `QTabBar::close-button` does). Monospace text uses `editorFont()`, not `QFontDatabase::systemFont(FixedFont)`, which ignores the zoom.

`applyZoom` sets the new application font *before* the zoomed style sheet as well as after it. Re-polishing for a new sheet gives every styled widget (explorer tree, menu bar, labels, buttons) the application font of that moment. With the font set only afterwards, those widgets stayed one step behind: after 230 % → Reset they still showed 230 %.

`ZoomPopup` is never zoomed. Its window has the property `qodeNoZoom`, which makes `scaleWidget` skip it and all its children, and it sets its own font back to 100 %. Under a style sheet, a child takes the application font rather than its parent's. The popup therefore gives each child that 100 % font explicitly. Without this, the popup grew and shrank under the pointer while the slider was being dragged.

Applying a zoom re-lays out the whole window, which takes a noticeable moment. The popup therefore shows a new value straight away and applies it at three points:

- when the slider handle is released;
- 250 ms after the last − / + click, so a run of clicks zooms only once;
- when the popup closes.

## cursors

`Application::eventFilter` gives every `QAbstractButton`, `QTabBar`, `QComboBox` and `QMenuBar` the pointing-hand cursor on first polish (unless the widget set its own).

## windows

File > New Window starts another QODE *process* (`--new-window` skips session restore). `app/InstanceRegistry` stops two windows editing the same project or file: each claim is a listening `QLocalServer` named by a hash of the path, and probing it is a local connect that returns immediately (stale sockets from crashes are replaced). `MainWindow` claims/releases the project, `EditorManager::syncFileClaims` the open files; a conflict shows an info dialog (session restore skips it silently).

## child processes outliving QODE

Servers (`DevServer` and its Spring / Ktor / Expo subclasses), Ktor's continuous build (`KtorReloader`) and the chat's `run_command` each run in their own process group (`setsid`), so stopping them kills the whole tree; the flip side is that nothing stops them when QODE ends without `closeEvent` (crash, `kill -9`, SIGTERM). `platform/ProcessTree` (Unix half, `ProcessTreeUnix.cpp`) fixes that: `ProcessTree::track(process)` sets the `setsid` modifier and registers the group (`+pgid` / `-pgid` lines) with a watchdog, which is this same binary started with `--qode-reaper` (handled first thing in `main`). The watchdog reads a pipe whose write end only QODE holds (`O_CLOEXEC`, so no other child inherits it); at EOF, however QODE ended (normal exit included), it SIGTERMs the groups still registered and SIGKILLs what is left after 3 s. It names itself `qode-reaper` and ignores SIGTERM/SIGINT/SIGHUP, so `pkill -x qode` does not take it down first. A Gradle `run` server's JVM is a child of the Gradle daemon, not in the group; it stops because the daemon cancels the build when its client (in the group) dies. Use `track()` instead of a bare `setsid` modifier for any new long-running child. Stop a tracked tree with `ProcessTree::stop(pid)` (SIGTERM to the group) and `ProcessTree::kill(pid)` (SIGKILL), never a raw `::kill`.

**Windows** (`ProcessTreeWin.cpp`): no watchdog. `track()` sets a create-process-arguments modifier that creates the process *inside* a Job Object of its own (`PROC_THREAD_ATTRIBUTE_JOB_LIST` in a `STARTUPINFOEXW` wrapped around Qt's `STARTUPINFOW`, so no child escapes before assignment; Qt never resumes a `CREATE_SUSPENDED` child, so that route does not work). The job has `KILL_ON_JOB_CLOSE`; QODE holds the only handle, so a crash or Task Manager ends every tree. When the root exits normally the flag is dropped and the handle closed (leftovers survive, as on Unix). `kill(pid)` = `TerminateJobObject`. `stop(pid)` = Ctrl+C on the tree's hidden console (QODE has none, so Qt starts each child with `CREATE_NO_WINDOW`, which gives it a hidden console of its own, shared by its descendants). Node / JVM / Python / cmd end on Ctrl+C; CTRL_BREAK would only make a JVM dump threads. QODE cannot send it itself: attaching to the console delivers the event to QODE too, and it died even with a handler installed (tested). So `stop` starts `qode.exe --qode-ctrl-c <pid>` (`DETACHED_PROCESS`, handled by `runIfWatchdog` in `main`), which attaches, ignores Ctrl+C, sends it and exits. If QODE has a console (started from a debugger), `stop` kills instead. Consequence: a Gradle daemon started by a tracked `gradlew` is in the job too, so it ends with an explicit stop or with QODE (Unix: it outlives both). Tested with a scratch program (python child + ping grandchild): stop → graceful in ~50 ms, kill ~5 ms, parent `TerminateProcess` → tree gone.

## platform layer (`src/platform/`)

OS-specific code lives here, one `.cpp` per OS behind a shared header, picked in `QODE.pro` with `unix:` / `win32:` file lists. Other modules call it and do not `#ifdef` on the OS themselves. `<windows.h>` is only included here (with `NOMINMAX` and `WIN32_LEAN_AND_MEAN`).

`Platform` (`PlatformUnix.cpp` / `PlatformWin.cpp`) also holds the following. Each Unix half returns exactly what the old inline code did.
- **Processes:**
  - `setShellCommand`: `/bin/sh -c` on Unix. On Windows it uses `cmd.exe /d /s /c "<line>"` as *native arguments*, because QProcess's C-runtime quoting is not what cmd parses.
  - `setCommand`: on Windows a bare name gets a PATHEXT lookup (`gradle` → `gradle.bat`), and `.bat`/`.cmd` files run through cmd with `cmdQuote`d arguments. No `%` is allowed in those arguments: cmd expands it.
  - `restartSelf` plus `runIfHelper`: the Windows helper `--qode-restart-after <pid>` waits for the old process (OpenProcess SYNCHRONIZE) and then starts QODE.
- **Wrappers:** `wrapperCommand/File/NeedsExecBit` give `./gradlew` / `sh gradlew` on Unix, and `.\gradlew` + `gradlew.bat` / `mvnw.cmd` on Windows.
- **Python:** `venvBinDir/venvProgram` give `bin/` on Unix and `Scripts\*.exe` on Windows.
- **Tools and PATH:**
  - `gitExecutable`: PATH first, then Git for Windows' install folders.
  - `extraBinDirs`: empty on Unix. On Windows: `%APPDATA%\npm`, pnpm, WinGet Links, Volta, `Program Files\nodejs`, and Scoop's shims.
  - `hasExecBit`: false on Windows, which hides Make Executable.
- **UI (Windows polish; every Unix half does nothing):**
  - AltGr: `initProcess` sets `QT_QPA_PLATFORM=windows:altgr` (an environment variable, not `-platform` in argv: a changed argv makes `QCoreApplication::arguments()` use argv instead of the Unicode command line) unless the user set it, and `initGui` (after the QApplication) removes it so children do not inherit it. Qt then reports AltGr as `GroupSwitchModifier`, not Ctrl+Alt, so the Ctrl+Alt shortcuts (G, C, E, N, H, R, Shift+S, Shift+C ...) no longer swallow `€ @ { [ ę ć ś`. `initGui` also installs an app-wide filter that drops `GroupSwitchModifier` from KeyPress / KeyRelease (the shortcut map already saw the key as a ShortcutOverride), so the editor reads AltGr+7 as plain `{` (auto-pairing needs no modifier), as on Linux. Left Ctrl+Alt+E still fires the shortcut. Before this, on a German layout AltGr+E opened the editor panel instead of typing €.
  - `setDarkTheme(t.dark)` (first thing in `Application::applyTheme`): `QStyleHints::setColorScheme` (Qt 6.8), so dark themes get dark title bars on every window and dialog even when Windows is set to light. Qt draws a dark frame only when its colour scheme is Dark *and* the window palette is dark; without the request the scheme follows the Windows setting. Each request refreshes Qt's theme, so only changes are sent (the first call always, which also pins it against later Windows setting changes).
  - `selectInFileManager(file)`: Reveal in File Manager selects the file in Explorer (`SHOpenFolderAndSelectItems`); Unix returns false and the folder opens as before.
  - Notifications: `app/DesktopNotify` has a Windows branch (no D-Bus there): a `QSystemTrayIcon` that is only in the tray while a notification is open, its balloon shown as a toast; a click on it emits `activated(key)`, `close(key)` removes the icon (and so the toast).

`AppPaths` (one `.cpp` for both OSes) builds every QODE-AGENTIC folder: `config()` (Unix `~/.config/QODE-AGENTIC`, Windows `%APPDATA%\QODE-AGENTIC`: settings, keys, `mcp.json`, `projects/`), `data()` (`~/.local/share/…` / `%LOCALAPPDATA%\QODE-AGENTIC`: language servers, history, scratches, web-preview storage), `cache()` (`~/.cache/…` / `%LOCALAPPDATA%\QODE-AGENTIC\cache`). Never build these from `QDir::homePath()` or `QStandardPaths` at a call site. `SettingsManager` opens `AppPaths::settingsFile()` with `QSettings::IniFormat` (Unix: the same `QODE.conf` as the old `QSettings(org, app)`; Windows: `QODE.ini`, because the native format there is the registry and `fileName()` then returned `\HKEY_CURRENT_USER\…`, which put the per-project JSONs into `<drive>:\HKEY_CURRENT_USER\` during the first Windows runs).

## what QODE leaves on a computer (transparency; Windows packaging)

Telling the user every folder, file, registry key and PATH entry QODE or its installer creates is a product goal ("no hidden stuff"). Rules:
- Everything QODE writes goes through `AppPaths`, or is listed in `app/QodeFiles::created()` (today: the Kotlin command link `~/.local/bin/kotlin-lsp[.cmd]` when it points into QODE's folder, and the JDKs QODE downloaded, recorded in `<data>/downloaded-jdks.txt` by `JdkInstaller` because `~/.jdks` is shared with IntelliJ / Gradle). Nothing goes into the temp folder for good (the New Project dialog's chevron PNG used to: now `<cache>/ui/`).
- **Help > QODE's Files** (`dialogs/QodeFilesDialog`): `QodeFiles::created(true)` with sizes (worker thread; `sizeOf` never follows links / junctions) and each folder one level down, plus `Platform::installedItems()` (Unix: program, `/opt/qode`, links, desktop entry, icons, man pages, `/usr/share/doc/<pkg>`; Windows: from the installer's uninstall key: install folder, shortcuts, PATH entry, Explorer menu keys, the uninstall key; portable / self-built: its folder) and `Platform::removalHint()`.
- **Registry (Windows):** QODE itself writes none. `QSettings(NativeFormat)` creates every key it opens, even to read (that left an empty `HKCU\…\Lxss` and the uninstall key), so `PlatformWin` reads only through `regString / regSubKeys / regKeyExists` (KEY_READ). Qt's file dialog writes `HKCU\Software\QtProject\OrganizationDefaults\FileDialog` on every close and cannot be redirected (always the registry there), so every picker is `FileDialogs::get…` (`dialogs/FileDialogs`): `Platform::saveQtDialogState` snapshots the key (and which keys exist, HKLM too: Qt's read fallback creates them when elevated), `restoreQtDialogState` writes the values back / deletes what did not exist. Unix: `AppPaths::initQtSettings` moves `QtProject.conf` into `~/.config/QODE-AGENTIC/`.
- **Portable (Windows):** `portable.txt` next to `qode.exe` → `AppPaths` roots in `<exe>\data\{config,local,local\cache}` (module path, works before the app object), JDKs in `data\local\jdks`, no Kotlin link (checkbox hidden), LSP removal allowed inside that folder.
- **Uninstaller helper:** `qode --qode-files list <report>` / `remove <report> <id>…` (`QodeFiles::runIfHelper`, first in `main`): ids are looked up in a fresh `created()`, never paths from the command line; folders via `Platform::removeTree` (junction-safe); report UTF-8 + BOM, tab-separated. Tested on a sandbox with a junction to a canary file.
- **Installer:** `packaging/windows/qode.iss` (Inno Setup ≥ 6.6: `CreateCustomForm(w, h, keepX, keepY)` changed signature), built by `scripts/win/build-installer.ps1 [-NoWeb] [-NoBuild] [-NoPortable]` / `build-all.ps1` into `dist-win\` (staging in `staging-win\<flavor>\`, emptied by the script). Per user (`PrivilegesRequired=lowest`), one AppId `{EF440086-…}` (= `Platform::kInstallerAppId`) for both flavours; `PrepareToInstall` uninstalls the installed one silently with `/KEEPDATA` first (so a web→noweb switch leaves no WebEngine file) and waits for its key to go. Tasks: PATH (`{app}\bin\qode.cmd` = `start "" "%~dp0..\qode.exe" %*`; never `{app}` itself, its Qt DLLs would shadow other programs'), Explorer "Open with QODE" (HKCU\Software\Classes), desktop icon. The Ready page lists everything it creates. `AppMutex=QODE-AGENTIC-running` (held by `Platform::initGui`). Uninstall (`usUninstall`, while `qode.exe` still exists): PATH entry removed (other entries byte for byte), then the data form (custom form, `TNewCheckListBox`, all ticked but JDKs), removal through the helper, and a summary of deleted / kept; silent: the defaults; `/KEEPDATA`: nothing. App-local MSVC runtime (VS `VC\Redist\MSVC\<v>\x64\Microsoft.VC*.CRT`) and the SDK's `Redist\D3D\x64` dxcompiler / dxil (windeployqt finds those only inside a VS environment).

## dialogs

new project / new file / unsaved-changes dialogs. `RunConfigDialog` edits the per-file-type run command (`SettingsManager::runCommand`, keyed by extension; `{file}`/`{dir}`/`{name}`/`{project}` are expanded and quoted); `MainWindow::runCurrentFile` (F5 / toolbar play button) saves, shows the terminal and types the command into the shell via `Terminal::runCommand`.

## project templates

File > New Project (`dialogs/NewProjectDialog`: template list + the chosen template's options) creates starter projects through `project/ProjectTemplates` (Qt Core + Gui for icon conversion; no dialog code inside). A template is a folder in `resources/templates/<id>/` — `template.json` (id, category, `order`, `icon` (a `resources/new-icons` file shown in the dialog's list, tinted muted), `attribution` (a copyright / trademark notice behind an info button beside the title: mandatory for Ktor), `mixins`, `requires` such as `jdk17`, `options` typed text/package/version/port (1-65535)/choice/bool/image, `imageOutputs`, `executable`, `openFiles`, `runCommand` stored as the project's run command, `when` = file/folder → `key`/`!key`/`key=value` switching it off; `requires` also takes `tool:<exe>[?key=value]` and `qt6`, all only warnings) and `files/` — with every file listed by hand in `resources/qode.qrc`. Shared trees live in `_shared/` (`gradle-wrapper` mixin: gradlew, gradlew.bat, jar, properties, and a `.gitattributes` keeping gradlew LF and *.bat CRLF in every clone whatever core.autocrlf says; the C / C++ / Qt templates carry the same for *.sh / *.bat) and all dependency versions in `_shared/versions.json` (`{{kotlinVersion}}`, `{{ktorVersion}}` …). Every `{{word}}` in a template file must be a known key or instantiation fails, so files that use the same syntax themselves (the Ktor template's `requests.http`) spell values out instead of using `.http` variables. The Ktor template (`kotlin-ktor`, from start.ktor.io: Netty, `application.yaml`, no plugins) takes Ktor itself from Ktor's published version catalog (`ktorLibs` in settings.gradle.kts, `io.ktor:ktor-version-catalog:{{ktorVersion}}`), so only `ktorVersion` pins the server modules and the plugin; checked to build and test on the shared Gradle 8.14.3 / Kotlin 2.2.21. Rendering: `{{key}}` in text files, lines holding only `{{#if key}}` / `{{#if !key}}` / `{{#if key=value}}` / `{{/if}}` toggle blocks, `__key__` and a leading `dot_` in file names, `.bat` gets CRLF, binaries (jar/png/ico…) are copied. Built-in keys: `name`, `appName`, `nameId`, `package`, `packagePath`, `maintainerName`, `uuid`, `year`, `gitIdentity`. `instantiate` writes to a sibling temp folder and renames it, so failures leave nothing. The image option is converted in-process (PNG sizes, ICO with PNG frames; a lettered placeholder when none is chosen). `MainWindow::newProject` instantiates, optionally `git init`s, opens the project and the template's `openFiles`; run commands come from the existing detectors (`JvmProject` also suggests `:hotRun --mainClass … --auto` for Compose Desktop). Plans: `plans/project-templates/` (git-ignored).
