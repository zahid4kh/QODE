# JVM, Gradle, Spring Boot and Ktor

## Run configurations for JVM projects

`project/JvmProject::detect` (replaces the Gradle-only detector; `project/GradleProject.*` is still listed in QODE.pro but nothing uses it) reads the root and its direct sub-folders: Gradle (Kotlin/Groovy DSL; `apply false` lines ignored) or Maven, Kotlin vs Java, and Compose Desktop / Android / Spring Boot / Quarkus / Micronaut / Ktor (`io.ktor.plugin`, or the start.ktor.io catalog alias `ktorLibs.plugins.ktor`) / JavaFX / `application` plugin / a declared `mainClass`; `src/main/{java,kotlin}` (+ `jvmMain`, `desktopMain`) are scanned for `main` functions (Kotlin file-level mains become `<File>Kt`, `@file:JvmName` and `@JvmStatic` honoured). Without an `application` plugin a found main runs through a Gradle init script that QODE writes to `~/.cache/QODE-AGENTIC/run/run-main.init.gradle` (registers a `qodeRun` JavaExec task, project untouched); Maven uses `exec:java -Dexec.mainClass=…`. `MainWindow::detectedRunCommand` returns the best command and fills `RunConfigDialog::setSuggestions` (the "Detected" combo; picking one fills the command).

**Build-file sync** (Java/Kotlin): saving a Gradle/Maven file (`LspManager::isJvmBuildFile`) sends `workspace/didChangeWatchedFiles` to the running java/kotlin servers (`syncBuildFiles`; jdtls then re-imports by itself); LSP > Sync Build Files (`MainWindow::syncBuildFiles`, also in the java/kotlin submenus) does the same for every build file plus `java.project.import`, and restarts a server that shows no progress within 5 s. jdtls reports progress as `language/progressReport` (not `$/progress`); `ServerState::syncing` drives the status-bar "⟳ Syncing build files…" text and `buildSyncFinished` the "✓ Build files synced" message.

**Version catalog completion**: `project/VersionCatalog` (Qt Core only) parses `gradle/libs.versions.toml` (found next to the script or in a parent folder, cached by mtime/size) and answers `libs.<a>.<b>.` in `*.gradle` / `*.gradle.kts` the way Gradle names accessors (`kotlin-stdlib` → `libs.kotlin.stdlib`; `libs.versions` / `bundles` / `plugins` sections). `CodeEditor::setLocalCompletions` (set by `MainWindow` for build scripts) feeds those items into the popup next to the server's, makes the file count as served, and snippets are hidden right after a `.`. The Kotlin server returns nothing in build scripts, so this is what completes there.

**Main functions** (`jvm/JvmTools`, Qt Core): `findMains` finds `fun main` (top level → the file facade `FooKt` / `@file:JvmName`; `@JvmStatic` in an `object` or `companion object`, the annotation may stand on the line above) and Java's `static void main(` (class = the types whose `{ … }` body holds it, nested ones joined as `Outer$Inner`; taking the last type declared before it ran `java Item` for a `record Item` declared above `main`), comments blanked first. `MainWindow::updateMainMarkers` (called from `updateHttpMarkers` for every non-.http file, on each edit) shows them as the editor's run markers; clicking one opens Run / Debug. `JvmProject::mainCommand(root, file, class, initScripts)` runs that class in its module: Gradle through the `qodeRun` init script (any module with the `java` plugin, application plugin or not; `JvmProject::runMainInitScript` writes it), Maven through `exec:java` (`-f module/pom.xml`). A file outside any build is compiled into `~/.cache/QODE-AGENTIC/run/` (`javac -g -d run/java-<name>`, `kotlinc -include-runtime -d run/<name>.jar`) and run from there, never next to the file. `java File.java` (the source launcher) is not used for this: it compiles without local variable tables and reports an uncaught exception from its own frame.

**Tests** (code lenses, see [editor.md](editor.md#code-lenses)): `JvmTools::findTests` finds functions annotated `@Test` / `@ParameterizedTest` / `@RepeatedTest` / `@TestFactory` / `@TestTemplate` (qualified or not; JUnit 4 / 5 and kotlin.test) with their class, and each class that holds some. It works on a copy of the text with comments and the insides of strings blanked (`codeOnly`, so a `"{"` in a JSON string does not count as a brace); the annotation's arguments and further annotations are skipped, then a Kotlin `fun name(` / ``fun `name with spaces`(`` or a Java method declaration must follow; the class is the innermost one whose braces contain it (nested classes joined with `$`; `Foo::class` and classes without a body are not classes here). `JvmProject::testCommand(root, file, class, method, initScripts, mavenDebugAgent)` shares the build / module / wrapper detection with `mainCommand` (`buildOf`): Gradle `[:module:]cleanTest [:module:]test --tests 'pkg.Class[.method]'` (cleanTest so an up-to-date test task still runs and a debugger is not left waiting), Maven `test -Dsurefire.failIfNoSpecifiedTests=false -Dtest='pkg.Class[#method]'`. `MainWindow::runTest` runs it in the terminal from the project root; Debug uses `debugInitScript(port, true)` (`~/.cache/QODE-AGENTIC/debug/debug-test.init.gradle`: the JDWP option on `Test` tasks, `maxParallelForks = 1`, `forkEvery = 0`, since two test JVMs would wait on one port) or surefire's `-Dmaven.surefire.debug`, then `launchDebug` as for a main. Checked: a JUnit 5 Java method (Run, and Debug stopping at a breakpoint in the test JVM) and a Ktor `testApplication` test in Kotlin.

**Package vs folder** (`JvmTools::folderPackage` / `packageMatches` / `withPackage`): below `src/<set>/java|kotlin/` the folder implies a package. Java must match exactly; Kotlin may leave out a common root package in its folders (`src/main/kotlin/Main.kt` with `package com.example` is fine, as its coding conventions allow). Saving a mismatching file puts a hint in the status bar; Alt+Enter (`MainWindow::localCodeActions`, which also carries C/C++'s Generate Definition and leads the code action menu even without a server) offers "Change package to '…'" (one undo step, only the differing range is replaced) and "Move file to …/" (through `MoveController`, which rewrites the references).

**Kotlin scripts** (`*.kts` that are not `*.gradle.kts`): F5 runs them whatever the project is (`MainWindow::runKotlinScript`, before the Spring / Ktor / web-server checks, unless the user set a `kts` run command): `kotlinc -script <file>` in the script's folder, or the file itself when it has a `#!…kotlin` line and is executable; with the shebang but no exec bit QODE offers Make Executable once per session. Run Configuration has `kts` presets (kotlinc -script, kotlin, direct) and `kt` / `java` ones that compile into the cache. Errors: the Kotlin server only analyses Gradle / Maven projects, so `jvm/ScriptCheck` compiles a script without running it (`kotlinc <file> -d ~/.cache/QODE-AGENTIC/kts/check-<hash>`, about 2 s; `*.main.kts` gets `kotlin-main-kts.jar` from the Kotlin home on the class path, so `@file:DependsOn` / `@file:Repository` resolve through kotlinc's own Maven cache) on open (when no server serves it after 800 ms) and on save; `parse` reads `file:L:C: error: …` plus the caret line for the range. `MainWindow::applyDiagnostics` shows the server's diagnostics when it has any, else kotlinc's (a server that analyses the script too would otherwise double every error). `JvmTools::kotlinHome` finds kotlinc's folder ($KOTLIN_HOME, the snap's `/snap/kotlin/current` — `/snap/bin/kotlinc` is a link to snapd —, the folder above the real kotlinc, SDKMAN).

**Dependencies** (Project > Dependencies… / Check Dependency Updates…; `jvm/DependencyDialog`, `jvm/DependencyEdit` (Qt Core), `jvm/MavenCentral` (Network)): search goes to `search.maven.org/solrsearch` (8 s timeout, two retries: it answers in well under a second but now and then takes 30 s); artifacts named exactly like a query word, with the word in their group too, come first (gson → `com.google.code.gson:gson`, not the forks). Versions come from the artifact's `maven-metadata.xml` on repo1 (current; the search index lags: it still said 2.14.0 for gson when 2.15.0 was out). Adding writes the way the build declares things: with `gradle/libs.versions.toml` and a build that uses `libs.` the library goes into `[libraries]` (`alias = { module = "g:a", version = "v" }`, alias from the artifact, group-prefixed when taken, an existing entry reused) and the build gets `implementation(libs.alias)`; otherwise coordinates (`implementation("g:a:v")` / Groovy `implementation 'g:a:v'`); Maven through `BuildFileEdit::insertMavenDependencies` (`compile` = no `<scope>`). A Gradle build with no `repositories` anywhere (module, root build, settings) also gets `repositories { mavenCentral() }`, or nothing resolves. Updates: `DependencyEdit::declared` finds literal versions in build files (`"g:a:v"`, Groovy maps), the catalog (`"g:a:v"`, `module` / `group`+`name` with `version` or `version.ref`; a shared `[versions]` key is listed once with the others in `sharedBy`) and poms (literal versions and `${property}` → the `<properties>` entry); six lookups at a time; `newestFor` skips pre-releases unless the current version is one. Files with unsaved changes are refused. For a `*.main.kts` (or any script outside a build) the dialog works on the editor's `@file:DependsOn` lines instead (unsaved, one undo step).

**Project JDK** (Project > Project JDK…, the status bar's Java button; `jvm/JdkScanner` (Qt Core), `jvm/JdkDialog`): JDKs from $JAVA_HOME, SDKMAN, /usr/lib/jvm, /usr/java, /opt/java, ~/.gradle/jdks (Gradle's toolchains), ~/.jdks (IntelliJ), mise, asdf and the `java` on PATH, each read from its `release` file (folder name as a fallback), deduplicated by canonical path. The choice is stored per project (`SettingsManager::projectJdk`) and applied by the terminal's startup command (`MainWindow::jdkStartupCommand`: `export JAVA_HOME=… PATH=…/bin:"$PATH"`, fish `set -gx`; joined with the venv activation), so new sessions and everything QODE runs in them use it; changing it offers to restart the open sessions. The dialog and the status bar warn when the build's `jvmToolchain(N)` / `JavaLanguageVersion.of(N)` has no installed JDK N, unless settings apply the foojay resolver.

**JDK for Gradle** (`JvmTools::gradleMinJava / gradleMaxJava / gradleRunsOn`, a copy of Gradle's compatibility matrix up to Gradle 9.9 / Java 27; a newer Gradle counts as running on any Java from its minimum): a Gradle only *starts* on the Javas it supports (8.7: 8-21, 8.14: 8-24, 9.1: 17-25, 9.9: 17-27). The Kotlin and Java servers import the build by running Gradle, so with only JDK 25 installed a Gradle 8.7 project imported nothing and the Kotlin server knew no classes (no completion, no definitions; its log says "There are no compatible JDKs found on the machine"). `JdkScanner::forGradle` picks the JDK: the project JDK if the wrapper's Gradle runs on it, else the system default, else the newest installed one it runs on. `LspManager::startServer` gives it to kotlin-lsp as `JAVA_TOOL_OPTIONS="-Dcom.jetbrains.ls.imports.gradle.java.home=<home>"` (the server's `GradleToolingApiHelper.findTheMostCompatibleJdk` returns that property as it is; JAVA_TOOL_OPTIONS reaches the JVM through the native launcher, quoted for paths with spaces) and to jdtls as `java.import.gradle.java.home`. `JdkScanner::needsOf` also checks the build's toolchain (a missing `jvmToolchain(N)` breaks the import too: NoToolchainAvailableException; Gradle counts the JVM it runs on as a toolchain) and says what to download. When something is missing, `LspManager::gradleJdkMissing` -> `MainWindow::offerJdkFix` (once per project and session): Download JDK N / Upgrade Gradle… / Project JDK…; the Java status button turns orange with the reason. Changing the project JDK, a download or a wrapper upgrade restarts the running Kotlin / Java servers.

**JDK download** (`jvm/JdkInstaller`, the JDK dialog's Download JDK…): Eclipse Temurin from api.adoptium.net (`/v3/assets/latest/<major>/hotspot`, the package's own SHA-256 is checked), unpacked with `Platform::setUnpackCommand` into `~/.jdks/temurin-<version>` (IntelliJ's folder, which JdkScanner, Gradle's toolchain detection and kotlin-lsp also search), then `java -version`. The same release already there is reused. It becomes the project JDK unless Gradle cannot run on it (a toolchain-only download).

**Wrapper upgrade** (Gradle panel > Upgrade…, also from offerJdkFix): `JvmTools::setWrapperVersion` first rewrites the distributionUrl of gradle-wrapper.properties (dropping an old distributionSha256Sum), then the terminal runs `<runner> wrapper --gradle-version X`: the old Gradle may not start at all (8.7 on JDK 25), the new one refreshes the scripts and jar.


**Status bar** (`MainWindow::updateJvmStatus`, on project open and when a build file, the catalog or the wrapper properties are saved): Kotlin version (plugin version where it is applied, the catalog's `kotlin`, gradle.properties, `<kotlin.version>`) → opens the file at that line; Java (toolchain or target: `jvmToolchain`, `JavaLanguageVersion.of`, `maven.compiler.release`, `java.version`, `sourceCompatibility`, `jvmTarget`; else "JDK N" of the JDK in use; ⚠ when the toolchain is missing) → the JDK dialog; Gradle wrapper / Maven wrapper version → its properties file. `JvmTools::detectVersions` reads the root and its direct sub-folders.

**New Kotlin Class/File / New Java Class** (explorer context menu on a folder below `src/<set>/java|kotlin` or holding sources, File menu for the current file's folder; `jvm/JvmNewFile` (Qt Core) + `dialogs/NewJvmClassDialog`): a name, or `sub.pkg.Name` (folders created, package extended), over a list of kinds (Kotlin: class, file, interface, data / value / sealed class, sealed interface, enum class, object, annotation; Java: class, interface, record, enum, annotation, abstract class, exception) picked with Up / Down from the name field, IntelliJ style. The package is what a Kotlin / Java file already in the folder declares (so Kotlin folders that leave out the root package still get it), else the folder's (`JvmTools::folderPackage`). Kotlin is offered in kotlin/ roots, next to .kt files, and in java/ roots of a module whose build mentions Kotlin; the file opens with the caret in the body.

**Copy Reference** (Ctrl+Alt+Shift+C, Edit menu, editor context menu; `jvm/JvmReference`, Qt Core): text only. Comments and literals are masked, declarations found with their brace ranges (Kotlin class / object / companion / fun / val; Java types and methods, statements like `return f(x);` excluded), and the result is the IntelliJ form: `pkg.Outer.Inner` for a type, `pkg.Outer#member` for a member, `pkg.topLevelFun` in Kotlin. Order: the declaration name under the caret, a type of the file, an import (or `as` alias), a member of the file with that name, else the function / type around the caret. Anything else (other languages, nothing to name) copies `relative/path:line`.

**Scratch files** (File > Scratch Files: New Kotlin Scratch Ctrl+Alt+Shift+Insert, Kotlin with dependencies `.main.kts`, Java; the 20 newest; Open Scratches Folder): files in `~/.local/share/QODE-AGENTIC/scratches/`, never in a project. They are plain scripts / Java files, so F5, the kotlinc check and the ▶ markers work as for any script.

**gradle.properties / local.properties / gradle-wrapper.properties** (`jvm/GradleProperties`, Qt Core): keys one dotted segment at a time (Gradle's `org.gradle.*`, Kotlin, kapt / KSP, Android, `systemProp.*` proxies; `sdk.dir` / `ndk.dir` / `cmake.dir`; the wrapper's keys), values after `=` (enums, the installed JDKs for `org.gradle.java.home` (cached 30 s), the Android SDK / its NDKs and CMakes, the current wrapper distribution). Names the build scripts read (`findProperty("…")`, `providers.gradleProperty("…")`, `property` / `hasProperty`, `extra["…"]`; `usedKeys`, cached by build-file mtime) are offered as keys too; the other way round, inside those calls in a build script the defined properties (`load`: the project's file, then `~/.gradle/gradle.properties`) complete with their value.

**Annotation completion** (`jvm/KotlinAnnotations`, Qt Core; wired in `MainWindow::wireJvmEdit` for .kt / .kts but not .gradle.kts): `@file:` lists JvmName, JvmMultifileClass, OptIn, Suppress and, in scripts, DependsOn / Repository / Import / CompilerOptions (snippets); `@` in a file no server analyses lists common annotations; arguments: `@file:DependsOn("…")` completes coordinates from `~/.m2/repository` and Gradle's module cache (read once, at most 1.5 s), and, 350 ms after typing stops, from Maven Central (`MavenCentral::search`; `group:artifact:` asks for its versions, merged with the downloaded ones newest first; answers cached per query, the list asked for again when one arrives); `@file:Repository("…")` common repository URLs, `@file:Import("…")` the scripts next to it, `OptIn(` the usual opt-in markers.

## Maven panel

`maven/MavenProject` (Qt Core) + `maven/MavenPanel` (right-hand island, View > Maven, the toolbar's Maven button; visible only when `MavenProject::buildDir` finds a pom.xml at the root or in a direct sub-folder; `window/MainWindowMaven.cpp`, created when first shown by `mavenPanel()`; IDE tool panel `maven`). Nothing is read by running Maven unless it has to be:

- **Header**: Execute Maven Goal… (free command line; the panel's options are added), Show Effective POM, Reload, close. Below: the folder, the wrapper's Maven version (`.mvn/wrapper/maven-wrapper.properties`) or "Maven on PATH" or a warning when neither `mvnw` nor `mvn` exists, and a "Make mvnw executable" button for a wrapper without its exec bit.
- **Options** (per project, `SettingsManager::mavenOptions`): Offline (`-o`), Skip Tests (`-DskipTests`), Profiles (a menu of every `<profile>` id in the poms, `activeByDefault` marked; `-Pa,b`), and in a multi-module build the Module the commands run in (`-pl :artifactId -am`; also decides whose plugins and dependency tree are listed).
- **Lifecycle**: clean … deploy; Ctrl+click several and they run together in lifecycle order (`mvn -DskipTests clean install`); context menu Run / Run with Arguments… / Run 'clean …' / Copy Command; the detail line shows the command and what the phase does.
- **Plugins**: from the effective POM when Maven is there (`help:effective-pom -Doutput=~/.cache/QODE-AGENTIC/maven/effective-pom-<hash>.xml`, run when the tab is first shown and after the poms change), else the packaging's default lifecycle plugins + what the root pom and the module declare. Goals come from the plugin's own `META-INF/maven/plugin.xml` in the local repository (`JarSource::readJarEntry`; goal, first sentence of the description, default phase), else a table of well-known goals; a plugin never downloaded says so. Goals run as `prefix:goal` (`maven-X-plugin` → X, `X-maven-plugin` → X).
- **Dependencies**: `mvn -B dependency:tree` parsed from its `[INFO]` lines (`parseDependencyTree`: one tree per module, depth from the `|  ` / `+- ` / `\- ` prefix, classifier and scope, `(optional)` notes); test / provided / optional entries dimmed; double-click a direct dependency opens its `<dependency>` in the pom; context menu Copy Coordinates / Copy as `<dependency>` / Open on Maven Central.
- Saving a pom reloads the panel while it shows (`pomStamp`). Commands go to the terminal through `MainWindow::runInTerminal` after Save All, so the terminal's problem scanner picks up `[ERROR] file:[L,C]` lines as for any Maven build. The status bar's build-tool button shows the Maven logo for Maven builds.

Checked against a two-module test project without Maven installed (lifecycle, options, profiles, modules, plugin goals from the local repository jars); the effective-POM and dependency-tree parsers are checked against Maven's output format only.

## Debugger

`debug/` (Qt Core + Network for the client, Widgets for the panel). The program runs in the terminal as usual, its JVM started with `-agentlib:jdwp=transport=dt_socket,server=y,suspend=y,address=127.0.0.1:<port>` (`DebugSession::agentOption`, a free port from `freePort`), so it waits for QODE before running anything; `DebugSession::start` attaches, trying every 300 ms for up to 10 minutes (the build comes first), and gives up when the Gradle build it waits for fails (`GradleBuildView::buildFinished`). How the agent gets in (`MainWindow::debugCommandFor`, `runMain`, `runKotlinScript`): Gradle gets `--init-script ~/.cache/QODE-AGENTIC/debug/debug.init.gradle`, which adds it to `JavaExec` tasks only (run, qodeRun, bootRun …; not Gradle's own JVMs); Maven gets `MAVEN_OPTS` (exec:java runs in Maven's JVM); a `java` command gets the option after `java`; kotlinc (scripts) `JAVA_OPTS`; anything else `JAVA_TOOL_OPTIONS`. Debug (Shift+F9) picks the current Kotlin script, else the main at or above the caret, else the project's run command (saved or detected).

`DebugWorker` is the JDWP client and lives on its own thread (`DebugSession` owns the thread and forwards everything as signals; late signals of a stopped session are dropped by a generation counter). Requests arrive as queued slots; inside one, commands are written and their replies awaited (`command`, with `waitForReadyRead`), and events that arrive meanwhile are queued and handled after it (`processEvents`); idle, events come in on `readyRead`. Breakpoints (`DebugSourceBreakpoints`: path, source name, declared package, lines) are placed per class: a `ClassPrepare` request with `SourceNameMatch` per source file (suspend all, so the breakpoint is in place before the class runs; the VM is resumed after) plus the already loaded classes of the package (`AllClasses`, then `SourceFile`); each line becomes a `LocationOnly` breakpoint at the lowest code index of that line in every method (lambdas and synthetic methods included). Breakpoints changed during a session are cleared and placed again. Uncaught exceptions stop too (`ExceptionOnly`, uncaught), unless the panel's check box was off when the session started. Steps: `SingleStep` LINE over / into / out with `Count 1` and `ClassExclude` for java.*, kotlin.*, kotlinx.*, jdk.*, sun.*, Gradle and friends (step into skips library code). Stopped, the worker sends the frames (class, method, source, line from the line table) and all threads; the panel asks for a frame's variables (`this`, then the live slots of the method's `VariableTable` — Kotlin's `$i$` inline markers left out —, read with `StackFrame.GetValues`; a script frame also lists `this`'s fields, which are the script's top-level vals) and for children on demand. Values: primitives, strings, boxed numbers by their `value` field, everything else by its `toString()` run in the stopped thread (`ObjectReference.InvokeMethod`, single-threaded, 2.5 s; an event during the call — a breakpoint inside toString — resumes that thread so the call can finish). Children are array elements (200), a `Collection`'s `toArray()`, a `Map`'s entries (key → value through `entrySet().toArray()` and `getKey` / `getValue`), or the fields of the class and its superclasses (statics left out; past 80 toString calls per request, objects show as `Type@id`). Evaluate takes `name`, `a.b`, `a[0]` (arrays, or a list through `toArray`), `x.size()` (methods without arguments) and Kotlin properties through their getters. Checked against Java (javac -g), Kotlin (a kotlinc jar), `kotlinc -script` and a Gradle `run` with the init script.

UI: `CodeEditor` breakpoints (`setBreakpointsEnabled` for .kt / .java / .kts; a click on a line number toggles one, Ctrl+F8 the caret line; a red disc behind the number and a tinted line; they follow edits like bookmarks) and `setExecutionLine` (warning-tinted line, an arrow, centred, folds opened). `MainWindow::m_breakpoints` (path → 0-based lines) is persisted per project (`SettingsManager::breakpoints`) and loaded in `onProjectOpened` before the files reopen. `DebugPanel` (right-hand island; Run > Debug Panel; created by `MainWindow::debugPanel()` when shown or when a session starts, then given the breakpoint list): status, the actions as buttons (Resume F9, Pause, Step Over F8, Into F7, Out Shift+F8, Stop Shift+F5), a thread combo, the frames (project files bold: `MainWindow::resolveSource` maps package path + source name to a project file, comparing declared packages where Kotlin folders do not follow them; the launched single file counts too), the variables tree with the evaluate box, and the breakpoints. Selecting a frame opens its line. The Run menu holds Run, Run Configuration, the debug actions, Toggle Breakpoint and the panel. Spring Boot / Ktor servers run from their own bars and are not debugged from here (Ktor's live routes already hold a JDWP connection).

## gradle

**Task timings** (`gradle/GradleEvents`, `gradle/GradleBuildView`, the Gradle panel's Build tab): every Gradle command QODE starts (`MainWindow::runInTerminal`: the panel's tasks, F5, the ▶ of a main, debugging) gets `--init-script ~/.cache/QODE-AGENTIC/gradle/events-<hash>.init.gradle` right after its runner. The script registers a `BuildService` that listens to `BuildEventsListenerRegistry.onTaskCompletion` (works with the configuration cache, unlike `TaskExecutionListener`) and appends one tab-separated `task` line per task (path, EXECUTED / UP-TO-DATE / FROM-CACHE / SKIPPED + reason / FAILED + message, start, end) to `events-<hash>.log`; the init script's body writes a `start` line and the service's `close()` an `end` line. A configuration cache hit runs no init script, so `parseLast` also starts a new build at a task line after an `end`. The view polls the file every 400 ms while it follows a build (ignoring an older build still in the file), shows BUILD SUCCESSFUL / FAILED with the total time and per-state counts, and lists the tasks with their result and a time bar scaled to the slowest; the compiler errors the terminal reported meanwhile (`ProblemScanner`, which now also reads Kotlin's `e: file:///…:L:C` and Maven's `[ERROR] …:[L,C]`) hang under the failed task and open their file. Checked with Gradle 8.14.3 (`gradle.services.get(BuildEventsListenerRegistry)` is internal API that has stayed in place).

**Wrapper** (the row under the panel's folder): the wrapper's Gradle version (`JvmTools::wrapperVersion` from `distributionUrl`); Upgrade… reads the current release from `services.gradle.org/versions/current` and, after a confirmation, runs `./gradlew wrapper --gradle-version X --distribution-type bin && ./gradlew wrapper` (the second run updates the scripts and jar from the new version); a `gradlew` without its exec bit gets a "Make gradlew executable" button instead (chmod on the user's click).

`gradle/GradleTasks` (Qt Core only) finds the Gradle build folder (`buildDir`: root, else first direct sub-folder with a build file, same places as `JvmProject`), picks `./gradlew` vs `gradle` (`runner`) and parses `gradle tasks` output into groups; `GradlePanel` shows them in the right-hand island and runs a task in the terminal. `MainWindow::m_gradleAct` (toolbar) / `toggleGradlePanel` opens it, visible only in Gradle projects.

## spring

Spring Boot (Gradle or Maven) projects; nothing shows unless `SpringProject::detect(root)` (Qt Core) finds a module applying the Spring Boot plugin (root + direct sub-folders; resolves `alias(libs.plugins.spring.boot)` through `gradle/libs.versions.toml`, `spring-boot-maven-plugin` / `spring-boot-starter-parent` in a pom). `command(Options)` builds `./gradlew --console=plain [:module:]bootRun [--args='--spring.profiles.active=… --server.port=… extra']` (Maven: `spring-boot:run -Dspring-boot.run.arguments=…`, or the user's complete replacement); options `{profiles, port, arguments, command}` live per project in `SettingsManager::springServer()` and are edited by `SpringConfigDialog`. `SpringServer` subclasses `DevServer` (which now has protected virtual `scan` / `adjustEnvironment` hooks): phase Building → Starting (at `> Task :bootRun`) → Running at the embedded server's "started on port N" line, `Started XApplicationKt in N seconds` fills `startupSeconds`, "Port N was already in use" / build failure give `errorString` (kept by `DevServer::onFinished`). `SpringBar` (toolbar strip, replaces the Run File / Run Configuration buttons like `DevServerBar`; owns the server) = status dot, `localhost:port` link, start/stop, restart, panel button (springboot.svg), settings; F5 (`MainWindow::runFile` / `springOwns`) starts or restarts it, `starting()` opens the panel when the right island is hidden. `SpringPanel` (right-hand island, `m_rightStack`; `MainWindow::toggleSpringPanel`, View > Spring Boot, only visible while a Spring project is open; created by `springPanel()` when the first Spring project opens, so it has the log from the first start) shows status / startup time / uptime plus the log tab: `SpringLogView` (a `QTextEdit`, not QPlainTextEdit — wrapped lines hang under the message via block margins) splits the raw output into entries (Logback/Spring lines, continuation lines attach to the entry above, Gradle/Maven output = Build, the rest Output, start/stop/fail = Marker), draws them with level colours, filters by level / text / build output, pauses, caps at 6000 entries, folds stack traces (exception lines + frames resolved to project files stay, framework frames hide behind a click-to-show line) and makes project frames / `e: file.kt:12:5` compiler errors links (`locationRequested` → `openFileAt`; frames are resolved against `ProjectFiles::files()` through the resolver `MainWindow` sets, cached until the index updates). An entry's draw position is tracked as `pos/len` in the document (`m_shown` = drawn entries) so appends, continuation lines (only the last entry changes) and fold toggles redraw just their own range. The panel has two tabs, Log and Requests: `HttpClientView` is a REST client (endpoint / history / saved lists, method + URL, headers, body; sends through `http/HttpRunner` and answers in the shared `http/HttpResponseView`, see [http.md](http.md); URLs starting with `/` resolve against the running port; list items can be copied as .http requests). `SpringEndpoints` (Qt Core) finds `@RestController` / `@Controller` classes in `SpringProject::sourceRoots()` by text scanning (comments blanked first; class + method mappings, `@RequestMapping(method=…)`, `@PathVariable` / `@RequestParam` / `@RequestHeader` / `@RequestBody`; Kotlin and Java) and builds a JSON body skeleton from Kotlin constructor properties / Java records (`SpringScan::bodySkeleton`); it is rescanned when the tab is shown. History (80, deduplicated), saved requests and the draft live per project in `SettingsManager::springRequests()`. `application*.properties|yml` get spring.svg in `explorer/FileIcons`.

**Run options** also hold `jvmArgs` (Gradle: `JAVA_TOOL_OPTIONS=…` prefix, since bootRun forks with the build's environment; Maven: `-Dspring-boot.run.jvmArguments`) and `env` (KEY=VALUE lines → `SpringServer::setExtraEnvironment`); `SpringConfigDialog` shows detected profiles (`SpringProject::profiles()`, files `application-<p>.*`) as check boxes synced with the profiles field.

**Config completion**: `SpringProperties` (Qt Core; built-in key table, one dotted segment at a time, value choices, YAML parents by indentation) feeds `CodeEditor::setLocalCompletions` for `application*.properties|yml` in `MainWindow`; `SpringProperties::load` flattens the default-profile config.

**Actuator tab** (`ActuatorView`, shown only when `SpringProject::hasActuator()`; health tree, beans, mappings, env, info, metrics; honours `management.server.port` / `base-path`; a 404 offers "Expose all endpoints" which appends to application.properties).

**Add Spring Starters…** (View menu → `AddStarterDialog`, catalog + `SpringStarters::plan` edit the module's build.gradle(.kts)/pom.xml with plain coordinates after the last main dependency (the insertion itself is `project/BuildFileEdit`, shared with Ktor plugins); Kotlin JPA also gets the `plugin.jpa` plugin, including a `kotlin-plugin-jpa` catalog entry; `Change::extra` carries the second file).

**New Spring Component** (explorer context menu through `ProjectExplorer::setNewMenuHook`, shown for folders below a source root; `SpringScaffold` writes Controller / Service / Entity / Repository / Configuration / ExceptionHandler in the folder's package, Kotlin or Java by source root;

**CRUD Set…** (`MainWindow::newSpringCrud`, `SpringScaffold::generateCrud` + `parseFields`) writes entity with typed fields, repository, service and a controller with list/get/create/update/delete in one go, refusing if any file exists).

The log view, `HttpClientView` and the config completion are shared with Ktor (below): `SpringLogView` also takes Logback lines with a date in front (Ktor's default pattern) and treats `> Task :run` like `bootRun` (application output starts); `HttpClientView::setScanTexts` rewords the endpoint list, `openEndpoint` / `endpointAsHttp` / `endpointAsCurl` serve the Ktor Routes tab, and endpoints are grouped by file + `controller` (Ktor: the declaring function). `SpringProperties::complete(…, ktor)` completes Ktor's keys (`ktor.deployment.*`, `ktor.application.modules`, `ktor.development`, `ktor.security.ssl.*`, `jwt.*`) instead of Spring's while a Ktor project is open; key details are UTF-8 (they were read as Latin-1, which garbled the dashes).

## ktor

Ktor servers (Gradle or Maven), built like the Spring Boot support; nothing shows unless `KtorProject::detect(root)` (Qt Core, root + direct sub-folders, same skip list as Spring) finds a module whose build names the *server* side: `io.ktor.plugin`, `ktor-server`, `ktorLibs.server.` / `ktorLibs.plugins.ktor` (Ktor's published catalog, start.ktor.io's current form), `libs.ktor.server` / `libs.plugins.ktor`, or `ktor-server` in a pom; `apply false` lines are ignored and a client-only build does not count. Only build files are read, so redetection on every build-file change (`KtorBar`'s watcher, 500 ms) is cheap. Detection also fills engine (Netty / CIO / Jetty / Tomcat from the dependencies or an `io.ktor.server.<engine>.EngineMain` main class), `mainClass` and the Ktor version (catalog import, `ktor = "…"` in a toml, `ktor_version` in gradle.properties, the plugin version, `<ktor.version>` in a pom). A Spring Boot application wins when both are present (`MainWindow::ktorAvailable`).

- **Run**: `command(Options, debugPort)` = `./gradlew --console=plain --init-script <cache>/ktor/run-<hash>.gradle [:module:]run [--args='-port=N -watch=… …']` (Maven: `[JAVA_TOOL_OPTIONS='…'] compile exec:java -Dexec.args=…`). Options `{port, development, autoReload, liveRoutes (default on), arguments, command, jvmArgs, env}` per project in `SettingsManager::ktorServer()`, edited by `KtorConfigDialog` (auto-reload also by the bar's ⚡ switch). The JVM options of the server (`jvmOptions()`: the user's, `-Dio.ktor.development=true` + `-Dktor.development=true` with development mode or auto-reload, `--add-opens=java.base/jdk.internal.loader=ALL-UNNAMED` with auto-reload, the JDWP agent with live routes) go through a Gradle init script that `KtorBar::launch` writes to `~/.cache/QODE-AGENTIC/ktor/` before each start (`runScript()`): it adds a `CommandLineArgumentProvider` to the module's `run` task, so the options reach only the forked server JVM (JAVA_TOOL_OPTIONS also reached the wrapper and daemon JVMs, and a JDWP agent there would be wrong) and come after the build's `applicationDefaultJvmArgs` (start.ktor.io writes `-Dio.ktor.development=$isDevelopment`, which used to win over ours). `ktor.development` as a system property is configuration to EngineMain (`getKtorEnvironmentProperties`), so it also beats `development: false` in application.yaml; `io.ktor.development` is what `embeddedServer` reads. Maven's exec:java runs the server inside Maven's JVM, so JAVA_TOOL_OPTIONS stays right there. The port goes in as `-port=N` (EngineMain reads it; `embeddedServer(port = …)` keeps its own). `KtorServer` (a `DevServer`): Building → Starting at `> Task :run` / exec:java / the first Ktor line → Running at `Responding at http://host:PORT` (the port is taken from there), `Application started in N seconds` = startup time; `BindException`, a failed build, a module that cannot be found and `Exception in thread "main"` become `errorString`; `PORT` is removed from the environment so a stray value does not move a `$PORT:8080` config. It also follows `Listening for transport dt_socket at address: N` (`debugPort()`), Ktor's reload lines (`Changes in application detected.` → `reloadStarted`, `Application auto-reloaded in N seconds.` → `reloaded`, `Application reload failed.` / `Auto-reload failed.` → `reloadFailed`) and the lines that say Ktor will not reload (`reloadBlocker()`: development mode off, no / non-matching watch patterns, an unsupported class loader). `KtorBar` mirrors `SpringBar` (owns the server, F5 through `ktorOwns`, Run Configuration opens `KtorConfigDialog`).
- **Live routes** (`KtorLive`, Qt Core + Network): the routes come from the running server's own routing tree, so routes built in loops, from computed paths or by plugins are right, and so is what a source scan cannot see (a routing function nobody calls). Ktor's official ways to list routes need changes to the project: `routingRoot.descendants()` / the runtime OpenAPI generator (`ktor-server-routing-openapi`) in the application, or the Ktor Gradle plugin's `ktor { openApi { enabled = true } }` compiler plugin (Kotlin 2.2.20+, preview in 3.6). QODE reads the same tree from outside instead: the server JVM gets `-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=127.0.0.1:<port>` and `KtorLive::read` (blocking, on a `QThread` from `KtorPanel::readLive`) speaks JDWP over `QTcpSocket`: `ClassesBySignature` + `Instances` find `EmbeddedServer.applicationInstance` and the `RoutingRoot` whose `application` is it (an application replaced by a reload can still be reachable); `RoutingNode.selector` / `childList` / `handlers` are read as fields (ArrayList `elementData`/`size`, the JDK's immutable / singleton / unmodifiable lists), selectors by class (`PathSegment*`, `RootRouteSelector.parts`, `HttpMethodRouteSelector.method.value`, `AuthenticationRouteSelector.names`, header `Upgrade: websocket` / `WebSocketProtocolsSelector` = WebSocket, accept `text/event-stream` = SSE, parameter / header / accept conditions, static content's own `TailcardSelector` and transparent selectors skipped). A handler of a plugin (`webSocket`, `sse`, `get<Resource>`) wraps the project's lambda: its captured fields are searched breadth first for a class outside `java/kotlin/io.ktor` with `invoke`/`invokeSuspend`; `SourceFile` + the lowest line of their line tables (inlined code is mapped past the end of the file) give the location, the class name the package and the declaring function. Only fields are read: nothing runs in the server and nothing is suspended; `VirtualMachine.Dispose` detaches. The agent listens again after a detach on the *same* address, which is why the bar picks a free port itself (`address=…:0` would move to a new port after every read). Reads: when the server is Running, after each reload, on refresh; one at a time. `KtorLive::merge` joins each live route with the scan's route of the same method + path (a `$x` template path matches the values a loop produced; static content / API docs match by prefix, one row per declaring call) for parameters, body, function and line; live routes without one are `runtimeOnly`, code routes the server lacks stay listed as `notServed`. The Routes tab says where its routes come from; without a debug port (setting off, custom command) or while stopped it is the scan's. ~100–200 ms for a few dozen routes.
- **Auto-reload** (`KtorReloader` + `KtorBar`): Ktor's development mode reloads changed classes itself (`EmbeddedServer.currentApplication`: the watch keys are polled when a call arrives, so a reload happens on the next request), from the class path entries that match the watch patterns as substrings. QODE adds the compile half and the trigger. A start with auto-reload begins a session (until stop, another project or the setting off): EngineMain gets `-watch=<module>/build/classes/,<module>/build/resources/` (Maven: `target/classes/`), `embeddedServer` watches its working directory by default. Once the start's own build is done (`> Task :run`, Running or Failed, so two builds never compile at once) `KtorReloader` runs `./gradlew --console=plain -t [:module:]classes`: Gradle's continuous build watches the sources itself, so edits from the editor, the QODE chat or git all count; its stdin stays open (end of input ends it). A round ends at `Waiting for changes to input files`; `BUILD FAILED` + `e: file:///…:L:C msg` lines make it Failed (errors go to the log, the bar shows "compile error", the server keeps the last good code); a round with `N executed` tasks emits `compiled`. Maven has no continuous mode: `mvn -q compile` runs after each saved source in the module (`KtorBar::sourceSaved`, 400 ms debounce). On `compiled` the bar sends `HEAD /__qode_reload__` (no route answers it) so Ktor reloads now; its log lines confirm it (`Reloaded in N s` marker, routes read again); no reload line within 3 s of the response restarts the server instead. Where an in-place reload would not change the code the server is restarted (`restartReason()`): a `reloadBlocker()`, or a module Ktor cannot load again by name. That last case was found the hard way: Ktor reloads a module through `Function.methodName()`, which needs a `KFunction`; `embeddedServer(…, module = Application::module)` with a plain `fun` is adapted to `suspend` by the compiler (a synthetic `…$main$1` class), and a trailing lambda is one too, so Ktor calls the module it started with and logs "auto-reloaded" while serving the old code. The running server answers this exactly: when the reload works even the first start loads the project's classes through `io.ktor.server.engine.OverridingClassLoader$ChildURLClassLoader`, otherwise they stay in the app class loader (`KtorLiveResult::codeReloadable`, from the handlers' `ClassLoader`); without a live read the scan decides (`embeddedModuleReloadable`: `module = X::name` naming a `suspend fun Application.name`). A restart after a continuous compile is quick (the run build is up to date), and a server that failed to start (a compile error, an exception) is started again by the next successful compile. Status: bar suffix "compiling…" / "reloading…" / "compile error" (amber dot), panel status + "reloaded in N s", log markers, Config rows "Auto-reload" and "Routes". Multi-module: only the server module's classes reload (sibling modules reach `run` as jars).
- **Panel** (`KtorPanel`, right-hand island, View > Ktor, toolbar button; IDE tool panel `ktor`; created by `MainWindow::ktorPanel()` when the first Ktor project opens): status / engine / version / startup / uptime and four tabs. **Log** = `SpringLogView`. **Routes** (`KtorRoutesView`): every route with the full path, method colour (WS / SSE for WebSockets and server-sent events), auth and kind, grouped by declaring function; filter + kind combo; double-click = source; menu: Open in Requests, Send, Open in Browser, Copy Path / URL / as .http / as cURL. **Requests** = `HttpClientView` with the HTTP routes (`KtorScan::http`), history / saved per project in `SettingsManager::ktorRequests()`. **Config** (`KtorConfigView`): engine, effective port and its source (run settings > `ktor.deployment.port` with `$PORT:8080` defaults > `embeddedServer` > 8080), host, development mode, version, how the server starts, the modules (`fun Application.x()` with the fqn the configuration uses, the loaded ones bold, listed-but-missing ones flagged), installed plugins (`install(X)`), authentication providers, every value of application.yaml / .conf (secret-looking keys masked) and the Ktor modules the build declares; rows with a source open it on double-click. Scanning happens when a non-log tab is shown and something changed (`sourcesChanged`: a saved .kt / application.* in the module, a build-file change, a start), debounced 400 ms.
- **Route scanner** (`KtorSource`, Qt Core): the routes while no server runs, and the parameters / bodies / lines the live routes are joined with. Comments and string contents are masked (offsets kept) so braces in them do not count; calls of the routing DSL are found with their generic, argument list and trailing lambda (member calls and `fun` declarations skipped). A route's path = the `route("…")` blocks around it + its own path (`path =` named argument, a literal, or a `const val` anywhere in the sources; `HttpMethod.X` in `route`/`method` gives `handle {}` its method). `fun Route.x()` / `fun Routing.x()` bodies are relative: every call of `x()` (outside member calls) is a mount, prefixes / `authenticate("…")` around the call carry over, recursively (cycle guard, at most 8 mounts), so one function mounted twice lists its routes twice; never called = listed relative and flagged "not mounted". Type-safe routing: `@Resource("…") class` paths nest through enclosing resource classes (`Articles.Id.Edit` → `/articles/{id}/edit`), `get<Articles.Id>` resolves by qualified then simple name, constructor properties (not `parent`) become query parameters with their defaults. Parameters read in a handler: `queryParameters["x"] ?: default`, `call.parameters` / `pathParameters` (path if the path has `{x}`), `getOrFail`, `request.headers[…]` / `header(…)`, `receive<T>()` / `val x: T = call.receive()` / `receiveText()` (body; Kotlin classes from `SpringEndpoints::parseFile` give the JSON skeleton). Also `webSocket`, `sse`, `staticResources` / `staticFiles` / `singlePageApplication`, `swaggerUI` / `openAPI`, `install(X)`, providers in `install(Authentication) { }` / `authentication { }`, `embeddedServer(Engine, port)`. Test sources are not scanned (`testApplication { routing { } }` is not the server). `KtorProject::readConfig` flattens YAML (lists joined with ", ") and HOCON (blocks, dotted keys, arrays over several lines, comments).
- **Add Ktor Plugins…** (View menu, Config tab; `AddKtorPluginDialog` + `KtorPlugins::plan`): 33 plugins by keys of Ktor's catalog (`server-contentNegotiation` → artifact `ktor-server-content-negotiation`, accessor `ktorLibs.server.contentNegotiation`), written the way the build already declares Ktor: `implementation(ktorLibs.…)` when settings imports Ktor's catalog; else new entries in the project's libs.versions.toml shaped like its ktor-server-core entry + `implementation(libs.…)`; else coordinates copying ktor-server-core's `-jvm` suffix and version (`$ktor_version` included); Maven copies the version element. Plugins needing `@Serializable` (JSON, Resources) also get the kotlinx.serialization compiler plugin next to the Kotlin one (`kotlin("…")`, `id(…)` or a catalog alias + a `kotlin-plugin-serialization` toml entry). The note after adding lists the `install(…)` lines.
- **File icons**: `FileIcons::setConfigBrand(Ktor)` (set by `updateKtorUi`) gives application.yaml / .yml / .conf the Ktor logo instead of Spring's leaf.
- **Template**: File > New Project > Kotlin > Ktor Server (see [app.md](app.md#project-templates)); the info button beside its title shows JetBrains' trademark notice, which must stay.

The chat's debugger tools drive the same `DebugSession`, breakpoints and `startDebug` (`window/MainWindowIdeDebug.cpp`); see [agent.md](agent.md).

## Linux and Windows

- **Wrappers:** `./gradlew` / `./mvnw` on Linux, `.\gradlew.bat` / `.\mvnw.cmd` on Windows. Use `Platform::wrapperCommand` / `wrapperFile` / `wrapperNeedsExecBit`. Readers of run commands accept every form, so a config saved on one OS still works on the other.
- **Run through `Platform::setCommand`** (wrappers and `kotlinc.bat` are `.bat` files on Windows), and stop with `Platform::killTree` or `ProcessTree::stop`. On Windows a plain kill only ends cmd.exe and leaves the JVM running.
- **JDKs:** `JdkScanner` asks `Platform::jdkFolders` / `jdkHomes` (Linux: nothing extra; Windows: Program Files vendor folders, the registry, Scoop, `.jdks`). `realPath` follows Windows junctions (Oracle's `Java\latest`), so a JDK is listed once. JDK downloads unpack with `setUnpackCommand`.
- **Gradle init scripts** (events, timings): file paths inside Groovy / Kotlin must use forward slashes, or escape backslashes.
- **Debugger, Ktor routes over JDWP, Spring actuator:** sockets only, no OS code. The debug launch lines were checked in PowerShell and cmd.
- The Ktor server and auto-reload use `ProcessTree::track` / `stop` (a process group on Linux, a Job Object on Windows), never `::kill`.
