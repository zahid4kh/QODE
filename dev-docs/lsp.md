# Language servers (LSP)

## lsp

language-server client; servers are never bundled, only found on `PATH` (or `SettingsManager::lspServerPath(id)`, set via the LSP menu). `LspServers` is the registry (`LspServerSpec`: id, executables incl. `name-N` variants, args, extensions, install help; add a language by adding a spec there). `LspClient` is one server process: `QProcess`, `Content-Length` framing, request/notify/callbacks, does the initialize handshake itself and answers the server's own requests with defaults. `LspManager` (owned by `MainWindow`) starts a server lazily when the first matching file is opened (root = project root, else the file's folder), tracks each `Document` (didOpen / debounced didChange / didSave / didClose, Save As re-opens under the new URI), restarts a crashed server twice, and stores `publishDiagnostics` per path; `MainWindow` forwards them to `CodeEditor::setDiagnostics` (wavy underlines in `refreshSelections`, tinted line numbers, tooltip in `viewportEvent`). UI: the top-level **LSP** menu and the status-bar button share one `QMenu` rebuilt on `aboutToShow`: one submenu per known server (coloured status dot; sections Set up / Server / Remove built with `QWidgetAction` captions), then Project (compiler flags) and Diagnostics.

**Document sync**: `Tracked::sent` is the text every server holding the document has (set by didOpen and each didChange). `LspManager::flushDocument` (one document of the debounced `flushChanges`) sends servers whose `textDocumentSync.change` is 2 (incremental: clangd, jdtls, tsserver, rust-analyzer, pyright …) only `LspSync::contentChange(sent, text)`: the range between the common prefix and suffix of the two texts plus the text that replaces it, so several edits within one debounce become one change spanning them. Diffing at flush time instead of collecting `QTextDocument::contentsChange` events avoids that signal's quirks (whole-block ranges on format changes, the off-by-one at the end on `setPlainText`). Positions are UTF-16 (the only `positionEncodings` we offer), never split a surrogate pair, and count lines by `\n` (`Document::text()` has no `\r`). Servers with full sync still get the whole text. A text that ends up as it was (typed and undone) sends nothing. `sendOpen` flushes pending edits to the servers already holding the document before a companion or restarted server opens it, so all of them stay at the same version. `LspSync` (Qt Core only) also holds the token-delta and glob helpers below.

**Moves and renames**: QODE rewrites imports itself (`refactor/MoveController`), so `willRenameFiles` (where the server would return those edits) is not used: both sets of edits would apply. After a move, rename or undo, `MoveController::filesMoved` → `LspManager::filesMoved` sends `workspace/didRenameFiles` to servers that registered `workspace.fileOperations.didRename` (filters matched by `LspSync::fileOperationMatches` / `globMatches`: `**`, `*`, `?`, `{a,b}`, `[!x]`, file / folder). Every running server also gets `workspace/didChangeWatchedFiles`: the old paths deleted, the new ones created (a moved folder as its files, up to 5000), and the closed files whose imports were rewritten on disk changed. Open documents follow through `documentPathChanged` (didClose + didOpen) and their edits through didChange. Without these events, jdtls and pyright kept the old file in their index.

**Large files** (`Document::isLarge`: over 2 million characters or 50 000 lines when loaded) are never tracked (`track` returns early): every edit would have the server parse the whole file again, with tokens, symbols and folding ranges for all of it crossing the pipe and being parsed on the GUI thread.

**Remove Language Server…** opens the modeless `dialogs/LspRemoveDialog`: for the downloaded Kotlin server it runs visible `rm` steps (link, `~/.local/share/QODE-AGENTIC/lsp/kotlin`, the index cache, optionally the library-source cache) and clears a saved path pointing there; for clangd (a system package) it shows the apt/dnf/pacman/zypper command, with Copy and Run in QODE Terminal; both end by offering `MainWindow::restartApplication`. Projects without a compile database get user-edited fallback flags: **LSP > Project Compiler Flags…** (`dialogs/CompilerFlagsDialog`, raw text stored per project as `lspFlags` in the project JSON, `{project}` expanded, parsed by `LspManager::parseFlags`) are sent as clangd's `initializationOptions.fallbackFlags` (`LspServerSpec::fallbackFlags`), so nothing is written into the project folder; saving restarts the server.

**Include paths**: **LSP > Include Paths…** (`dialogs/IncludePathsDialog`, `SettingsManager::includePaths`, per project, entries absolute / root-relative / `{project}`) become `-I` fallback flags; because clangd ignores fallback flags for files a compile database covers, `LspManager::preparePatchedDatabase` writes a copy of the project's `compile_commands.json` (root or `build/`) with the `-I` flags appended to `~/.cache/QODE-AGENTIC/lsp/clangd-db/<hash>/`, passes `--compile-commands-dir`, and rebuilds it (file watcher) when the original changes. `compile_flags.txt` projects keep using that file. `project/QmakeProject` is a best-effort `.pro` reader (assignments, `$$VAR`, `include()`, SUBDIRS, platform / `greaterThan(QT_MAJOR_VERSION…)` conditions evaluated for Linux; Qt header paths from `qmake -query`): `LspManager::startServer` prepends its `compilerFlags()` to the user flags when there is no compile database, `buildFileSaved` restarts the server when a `.pro`/`.pri` is saved, and `MainWindow::configureRun` prefills `QmakeProject::runCommand()` (out-of-source build in `build/`) for C++ file types of a qmake app project. Implemented: diagnostics, hover (`CodeEditor::hoverRequested` on a tooltip over an identifier → `LspManager::hover` → `CodeEditor::showHover` renders the Markdown; diagnostics under the mouse stay in the tooltip) and Go to Definition (F12 / Ctrl+click, Ctrl+hover underlines the identifier via `CodeEditor::updateLink` when `setDefinitionAvailable` says a server serves the file → `MainWindow::goToDefinition`, several results go in a popup menu); completion (`CodeEditor::completionRequested` → `LspManager::completion` → `CodeEditor::showCompletions`: auto-trigger on identifier chars and `.` / `->` / `::`, Ctrl+Space manual, stale answers dropped by token; `CompletionPopup` is a non-focus-taking list that filters/ranks locally, `CodeEditor::acceptCompletion` applies the item's textEdit plus additionalTextEdits such as `#include` in one undo step; snippets are not advertised; with no server Ctrl+Space offers words of the document); clangd uses `compile_commands.json` / `compile_flags.txt` from the root or `build/`.

**Kotlin** (JetBrains' `kotlin-lsp`, spec id `kotlin`, `--stdio --system-path={cache}`; `{cache}` is expanded by `LspManager::startServer` to `~/.cache/QODE-AGENTIC/lsp/<id>/<hash of root>`): the server uses *pull* diagnostics (`LspManager::pullDiagnostics` after open/change/save and on `workspace/diagnostic/refresh`, shared `setDiagnosticsFor` with the push path), reports work via `$/progress` (see *Server status* below) and logs through `window/logMessage` (kept in the client log). `LspInstaller` (+ `dialogs/LspInstallDialog`, LSP menu > Download and Set Up…, `LspServerSpec::installable`) downloads the standalone archive `kotlin-server-<ver>.tar.gz` from download.jetbrains.com (pinned `LspInstaller::pinnedVersion()`, "latest" via the GitHub API is opt-in), verifies SHA-256 (the pinned x64 hash is also hard-coded), unpacks with `tar` into `~/.local/share/QODE-AGENTIC/lsp/kotlin/<ver>/`, repoints `current`, links `~/.local/bin/kotlin-lsp` (only replaces its own symlink) and test-runs `--version`; the archive bundles its own JBR so no system Java is needed. `LspServers::locate` order: configured path, PATH, then the managed `current/bin/intellij-server`. The server only analyses Gradle/Maven projects.

**Web servers** (ids `typescript` = typescript-language-server for ts/tsx/js/jsx/mjs/cjs/mts/cts, `html`, `css` = vscode-css for css/scss/less, `json` = vscode-json for json/jsonc; all `--stdio`, `needsNode`): installed by `LspServerSpec::Installer::Npm` — `lsp/NpmInstaller` runs `npm install --prefix ~/.local/share/QODE-AGENTIC/lsp/web typescript@6 typescript-language-server vscode-langservers-extracted` (one shared `managedId` = "web", so `LspServers::sharingInstall` refreshes/removes all four together; `dialogs/NpmInstallDialog` shows npm's live output, `LspRemoveDialog::buildNpm` deletes the folder; the managed id is passed to both). `typescript` is pinned to 6 because 7 is the native port with no `tsserver.js`; `LspManager::startServer` passes `initializationOptions.tsserver.path` (project `node_modules/typescript` first, else the managed copy) since the server does not find TypeScript next to itself. The servers are `#!/usr/bin/env node` scripts and a desktop-launched QODE lacks nvm's PATH, so `LspServers::nodeExecutable()` (PATH, then nvm/fnm/volta/asdf/system folders) feeds `LspClient::prependToPath`; a missing Node shows as "Node.js not found" in the LSP menu. The html/css/json servers use pull diagnostics (handled by the generic `pullDiagnostics`), typescript pushes. `LspServerSpec::languageIds` maps extensions to language ids (tsx → typescriptreact …) and `languageId()` sends `jsonc` for tsconfig/jsconfig/.eslintrc files.

**Bash** (id `bash`, `bash-language-server start`, `needsNode`): its own npm install, `managedId` `bash` (`NpmInstaller` takes the managed id: `packages("bash")` = bash-language-server, about 30 MB in `~/.local/share/QODE-AGENTIC/lsp/bash`), so it is set up and removed without touching the web servers. `NpmInstallDialog` and `LspRemoveDialog::buildNpm` word themselves by that id. It handles sh/bash/ksh and the `.bash*` dotfiles, all as language id `shellscript`. `LspServerSpec::interpreters` also gives it files without an extension whose `#!` line names sh/bash/dash/ksh (`languageIds[""]`). zsh is left out because ShellCheck refuses zsh scripts. Its diagnostics come only from a system `shellcheck` on PATH (npm does not provide it): the install dialog says whether it was found and how to install it. Without ShellCheck the server still gives completion, hover (man / help pages), definition, references, rename and symbols. Formatting goes through `format/Formatter`'s shfmt first, as before.

**Java** (Eclipse JDT LS, spec id `java`, `managedId` `jdtls`, `Installer::Jdtls`): `lsp/JdtlsInstaller` (+ `dialogs/JdtlsInstallDialog`) downloads the pinned milestone tar.gz from download.eclipse.org (SHA-256 checked, `latest.txt` for the opt-in latest) into `~/.local/share/QODE-AGENTIC/lsp/jdtls/<ver>/` with a `current` link; the server needs a system JDK 21+ (`LspServers::findJava`: JAVA_HOME, PATH, JDK folders; a JAVA_HOME pointing at an older JDK does not hide a newer one). No Python wrapper is used: `LspServers::jdtlsCommand` builds `java … -jar plugins/org.eclipse.equinox.launcher_*.jar -configuration <cache>/config -data <cache>/data` (a packaged `jdtls` wrapper is run with `--java-executable`), cache = `~/.cache/QODE-AGENTIC/lsp/java/<hash of root>`. `.project`/`.classpath`/`.settings` stay out of the project only with both the JVM property `-Djava.import.generatesMetadataFilesAtProjectRoot=false` and `workspace/didChangeConfiguration` after init (`javaSettings` in LspManager.cpp). jdtls adds an item's import only on `completionItem/resolve` (`LspServerSpec::resolvesCompletions` → `LspCompletionItem::resolveData` → `CodeEditor::setCompletionResolver` → `LspManager::resolveCompletion`); library classes come back as `jdt://` URIs, fetched with `java/classFileContents` and cached read-only by `JarSource::storeText`; the client-side command `java.apply.workspaceEdit` is applied in `runCodeAction`. A missing/old Java shows as status Crashed with the reason (Restart Server retries). Removal (`LspRemoveDialog::buildManaged`) deletes the install, `~/.cache/QODE-AGENTIC/lsp/java` and optionally the library-source cache.

**Diagnostics for a version** (used by the QODE chat's check after an edit and its `get_diagnostics`, see [agent.md](agent.md)): `Tracked::reported` is the newest document version the file's main server reported on, `diagnosticsVersion(doc)` returns it, and `diagnosticsReported(path)` fires on every report, also one that changed nothing (`setDiagnosticsFor` returns early on an unchanged list, so `diagnosticsChanged` cannot tell "checked, same result" from "not checked yet"). A `publishDiagnostics` with `version` counts for that version, one without for the version the server has now. A pull counts for the version it was sent for, but only when the server has no `$/progress` running: a pull is answered at once, and kotlin-lsp answers an empty list while it is still importing, then asks for a refresh (measured: the real errors came 2.3 s later). A push server publishes only after analysing a version, so no such rule is needed there (clangd's long background indexing would otherwise hold up every check). `syncNow(doc)` sends the debounced didChange at once and returns the version sent (it pulls again if the current version has no answer, in case an earlier pull failed); `tracks(doc)` says whether a server is meant for the file at all. `reported` is reset when the main server stops.

**Companion servers** (`LspServerSpec::companion`, `LspServers::companionsFor`): `eslint` (`vscode-eslint-language-server`, part of vscode-langservers-extracted) and `tailwindcss` (`@tailwindcss/language-server`, added to `NpmInstaller::packages`) never become a file's main server (`forFile` skips them) but every document they apply to is opened in them too, only for projects where `spec.relevant(root)` holds (`hasEslint`: `node_modules/eslint` + a config; `hasTailwind`: tailwindcss dependency / `tailwind.config.*`). `LspManager::Tracked` therefore has `serverId` (main) + `companions` and `openOn` (servers that got didOpen); `servers()` lists all of them, didOpen/didChange/didSave/didClose/pull-diagnostics go to each, diagnostics are stored per server (`m_diagBySource`, merged into `m_diagnostics` by `publishMerged`, `LspDiagnostic::server`), and completion / hover / codeAction / documentColor merge the answers of every ready server (`readyClientsFor`; completion delivers after 400 ms at the latest so a slow companion cannot block the popup). Companions ask for settings through `workspace/configuration`: `LspClient::setConfigurationProvider` (advertised only when set) is fed by `configurationFor` in LspManager.cpp (ESLint needs a full settings object incl. `experimental: {}` or it throws on `useFlatConfig`; ESLint uses pull diagnostics; its `eslint/*` server requests are answered in `LspClient::handleServerRequest`). The status-bar button ignores companions. The html/css/json servers only format when started with `initializationOptions.provideFormatter` (set in `startServer`).

**Document links**: `LspManager::documentLinks` merges `textDocument/documentLink` from every ready server with `documentLinkProvider` (links without a `target`, which need `documentLink/resolve`, are dropped); see [editor.md](editor.md#ctrlclick-links). It is a background request in the typing-first queue.

**Colours**: `CodeEditor::colorsRequested` (450 ms after an edit, plus a retry timer in MainWindow on every status change) → `LspManager::documentColors` → `CodeEditor::setColorSwatches` (swatch cursors follow edits; the gap in front of each colour is laid out by `SyntaxHighlighter::setGapProvider` as extra letter spacing on the preceding character — extra selections cannot change layout — and the square is painted in `paintSwatches`); a click emits `swatchClicked` → `MainWindow::pickColor` (QColorDialog → `colorPresentation`, notation kept: #hex / rgb / hsl).

**Rename / references**: F2 `MainWindow::renameSymbol` (prepareRename → input box → `textDocument/rename` → `applyWorkspaceEdit`, CSS selectors keep their `.`/`#`), Shift+F12 `findReferences` → `dialogs/ReferencesDialog`; both go to the file's main server only. Bookmarks moved to Shift+F2 (next) / Ctrl+Shift+F2 (previous) / Ctrl+F2 (toggle). Unlike the Kotlin archive, these need a system Node.js (typescript-language-server asks for Node >= 22). Unused imports (Kotlin): the server publishes no unused-import diagnostic, so `LspManager::unusedImports` runs `kotlin.organize.imports` with its `workspace/applyEdit` intercepted (`m_capturing`) and treats import lines missing from the proposed text as unused; `MainWindow` runs it 1.2 s after diagnostics settle (`m_importTimer`) and feeds `CodeEditor::setUnusedImports` (gray via extra selections on cursors that follow edits). Hovering a gray import shows a `HoverPopup` with a link → `removeUnusedImportsRequested` → `UnusedImportsDialog` → `CodeEditor::removeLines`. Import lists fold as one region (`CodeEditor::importRunEnd`, chevron always visible on the first import). Library navigation: the server answers definitions in dependencies with `jar:///…-sources.jar!/pkg/X.kt` (and the JDK's `src.zip`) URIs; `lsp/JarSource` unpacks that entry (own zip reader + zlib, `-lz`) into `~/.cache/QODE-AGENTIC/lsp/library-sources/` as a read-only file which opens like any other, while `LspManager` keeps tracking it under its jar URI (`JarSource::uriForPath`). Imports: **Alt+Enter** (`CodeEditor::codeActionsRequested` → `MainWindow::showCodeActions` → `LspManager::codeActions` / `runCodeAction`) lists the server's quick fixes ("Import → java.io.File", organize imports, refactorings); the client advertises `workspace.applyEdit`, and `workspace/applyEdit` is answered through `LspManager::setApplyEditHandler` → `MainWindow::applyWorkspaceEdit` → `CodeEditor::applyTextEdits` (one undo step per file). Kotlin completion items carry `command: jetbrains.kotlin.completion.apply` instead of a text edit (that command adds the import and inserts the text): `CodeEditor::acceptCompletion` hands such items to `setCompletionCommandRunner` → `LspManager::runCompletionCommand`, which re-requests completion at the current caret (the server's session is stale once more was typed), picks the same label/detail and runs the command, falling back to local insertion.

## LSP assists (web servers first, any server that advertises the capability gets them)

all requests go through `MainWindow` ([MainWindowAssist.cpp](src/window/MainWindowAssist.cpp): `wireAssists` per editor, `createAssistActions`), the editor-side state lives in [CodeEditorAssist.cpp](src/editor/CodeEditorAssist.cpp).

**Signature help**: `CodeEditor::signatureTyped` asks after the server's trigger characters (`LspManager::signatureTriggers`), every caret move while the popup is open re-asks (the server answers null once the caret leaves the call), Up/Down cycle overloads, Esc closes, Ctrl+Shift+Space opens by hand; `editor/SignaturePopup` shows the signature with the active parameter highlighted.

**Hover** and the completion documentation render through `editor/HoverRender` (Markdown → HTML; fenced code is coloured with `SyntaxHighlighter` on a scratch document, so it follows the theme); the hover popup ends with *Go to Definition · Find References* (+ *Quick Fix…* when a diagnostic sits there) links, handled in `CodeEditor::showHover`; a `-` inside a name counts as part of the word (Tailwind classes).

**Completion details**: `LspCompletionItem::resolveData` is kept for every server that has `completionProvider.resolveProvider`; `CompletionPopup::currentItemChanged` → `CodeEditor::updateCompletionDocs` (140 ms) asks `completionItem/resolve` and shows documentation + the long detail ("Auto import from './utils'") in the docs frame beside the list (`CompletionPopup::showDocs`, results cached in `m_docCache`); `LspServerSpec::resolvesCompletions` (java, typescript) additionally resolves on accept, because typescript-language-server delivers the auto-import edit only there.

**Inlay hints**: `CodeEditor::inlayHintsRequested` (500 ms after an edit/scroll, visible lines ± 80) → `LspManager::inlayHints`; the hint's room is letter spacing on the preceding character (the same trick as colour swatches: `SyntaxHighlighter::setGapProvider` now returns `(column, pixels)` pairs, `CodeEditor::gapColumns` merges swatches and hints) and `paintInlayHints` draws the pill. typescript-language-server reads its hint preferences only at start (`LspManager::tsPreferences` enables every kind in `initializationOptions.preferences`; a later `didChangeConfiguration` is ignored), so the editor filters by kind (1 type, 2 parameter) using `SettingsManager::inlayParameterHints/inlayTypeHints` (View > Inlay Hints, both off by default).

**Kotlin** reads its hint options (map option id → bool: `hints.parameters`, `hints.parameters.compiled`, `hints.type.*`, `hints.lambda.*`) from `workspace/configuration` section `jetbrains.kotlin` on *every* request (`configurationFor`, from the same two settings; a null answer makes the request fail), and sends one hint per label part at the same spot, which `LspManager::inlayHints` merges into one pill; hints are only complete once the server has analysed the Gradle project (root must be the project root).

**Symbol highlights**: `caretSettled` (300 ms) → `LspManager::documentHighlights` → `setSymbolHighlights` (extra selections, dropped when the caret leaves the uses; View > Highlight Symbol Under Caret).

**Light bulb**: on `caretSettled` the bulb is requested only when a diagnostic touches the caret line (or a selection exists) with `only: ["quickfix"]` + `triggerKind: 2`; drawn in the gutter by `paintLightBulb` (the gutter reserves `kBulbWidth` while enabled), a click = Alt+Enter.

**Code actions**: the Alt+Enter menu groups Quick Fix / Refactor / Source Actions (`MainWindow::showCodeActions`); lazy actions are resolved first (`codeAction/resolve`, the client advertises `resolveSupport: edit`), bare Commands run through `workspace/executeCommand`; `_typescript.rename` (after "Extract to …") is answered by opening the rename box at the new name; `applyWorkspaceEdit` handles create / rename / delete operations and a text edit for a file that does not exist yet ("Move to a new file"); `CodeEditor::applyTextEdits` orders equal-start edits by range length then list order.

**Source actions**: Edit > Source Actions (Organize Imports Shift+Alt+O, Remove Unused Imports, Add Missing Imports, Fix All) call `LspManager::applySourceActions` — per kind and per server, one request and one applied action at a time so each sees the previous result (ESLint's `source.fixAll.eslint`, TypeScript's `source.organizeImports.ts` …); File > Save Options > *Fix All on Save* / *Organize Imports on Save* (`SettingsManager::fixOnSave/organizeImportsOnSave`, per project like Format on Save) run the same through `EditorManager::setLspFixer` → `applySourceActionsBlocking` (3 s, cancelled steps never touch the document later) before the formatter.

**Renaming a file in the explorer** emits `ProjectExplorer::renameRequested`, handled by `MoveController::rename` (the drag-and-drop mover's planner: imports, includes and links follow, with Undo); without a handler the explorer renames by itself.

## LSP file-wide data (any server that advertises the capability; verified against kotlin-lsp 263)

`CodeEditor::serverDataRequested` (450 ms after an edit, plus a retry on server status changes / `workspace/semanticTokens|foldingRange/refresh` → `LspManager::semanticTokensRefresh`) makes `MainWindow::requestServerData` ask for three things; each answer is dropped unless `document()->revision()` still matches.

**Semantic tokens**: `LspManager::semanticTokens` decodes `textDocument/semanticTokens/full` against the server legend. Servers whose `semanticTokensProvider.full.delta` is true (clangd, rust-analyzer, jdtls …) are asked `full/delta` with the `previousResultId` kept in `Tracked::tokensResultId` / `tokensData` (the raw numbers, main server only, cleared on didOpen). `LspSync::applyTokenEdits` applies the edits from the back. When the cache no longer matches the id the delta was asked against (two requests in flight) or an edit does not fit, the cache is dropped and a full request goes out at once. Errors clear the cache, except "superseded" (held in `m_deferred` and replaced, so never sent). After an edit the answer is a handful of numbers instead of every token in the file; `CodeEditor::setSemanticTokens` maps types to `TokenRole` (`Variable/Property/Parameter/Constant` are new, backed by new `Theme` fields; namespace/keyword/string/number/comment/operator are deliberately not overlaid) and hands per-line tokens plus a `qHash` of each line's text to `SyntaxHighlighter::setSemanticTokens`, which paints them over the regex colours in `highlightBlock` only for lines whose text still hashes the same (edited lines fall back to regex until the next answer; `shiftSemanticLines` keeps line numbers aligned). View > Semantic Highlighting (`SettingsManager::semanticHighlighting`).

**Folding is a union**: `isFoldable` is true when QODE's own detection *or* a server range starts at the line, and `foldEnd` prefers the server's end (`serverFoldEnd`: the closing-bracket line stays visible like the client folds); import lists keep the client path (`importRunEnd`) so the import-fold persistence keeps working. Server ranges live in `CodeEditor::m_serverFolds` and are shifted by `shiftServerData` (called from `trackLineEdit`) so they follow edits.

**Symbols**: `CodeEditor::setDocumentSymbols` stores the `textDocument/documentSymbol` tree; `symbolChainAt` (breadcrumbs via `EditorManager::updateCrumbs`, sticky scroll) uses it instead of the indentation heuristics (`Breadcrumbs::chainFromSymbols`, leaf kinds such as properties are skipped) and Go to Symbol uses `Breadcrumbs::flattenSymbols`; without a server the regex versions remain.

**Completion capability `editsNearCursor`** (a clangd extension, ignored by other servers) lets clangd list a pointer's members after `.` with an edit that replaces the `.` by `->`; `CodeEditor::smartArrow` builds on it (see [editor.md](editor.md)).

**Switch Header/Source** asks clangd's `textDocument/switchSourceHeader` only after the name-based search in `CppTools::counterparts` came up empty (see [editor.md](editor.md)).

**Type definition** (Ctrl+Shift+F12) and **Go to Implementation** (Ctrl+Alt+F12) are `goToDefinition(..., LspManager::Navigate::…)` → `LspManager::definition(..., what)` (several results go in the usual popup menu).

**Go to Symbol in Workspace** (Ctrl+Alt+R, `MainWindow::showWorkspaceSymbols`) re-asks `workspace/symbol` of the current file's server 180 ms after each keystroke and feeds the `PalettePopup` (stale answers dropped by token).

**Call hierarchy** (Ctrl+Alt+H): `prepareCallHierarchy` + `callHierarchyCalls` (items carry their `server` id and raw JSON) feed `dialogs/CallHierarchyDialog`, a lazily expanding tree with a Callers/Callees switch.

**Type hierarchy** (Edit > Type Hierarchy…, Ctrl+Shift+H; Ctrl+H stays Replace): `prepareTypeHierarchy` + `typeHierarchy(item, supertypes)` (`typeHierarchy/supertypes|subtypes`, items parsed into `LspCallItem` like the call hierarchy) feed a second `CallHierarchyDialog` built with `Kind::Types` (Supertypes / Subtypes switch, own window `m_typeDialog`). An interface (SymbolKind 11) opens on Subtypes, anything else on Supertypes. Library types without source (jdtls's `java.lang.Object`) have no path: they show without a location and do not open. Checked with jdtls 1.61, clangd 18 (`struct Dog : Animal`), and kotlin-lsp advertises it.

**Code lenses**: `LspManager::codeLenses` (`textDocument/codeLens` of the main server, a background request in the typing-first queue), `resolveCodeLens` (`codeLens/resolve` when the server has `resolveProvider`, else the lens comes back unchanged; not queued, its params carry no document to de-duplicate by), `hasCommand` / `executeCommand`, and `locationsOf` (Location / LocationLink arrays). The client advertises `textDocument.codeLens` and `workspace.codeLens.refreshSupport`; `workspace/codeLens/refresh` joins semantic tokens / folding ranges in `serverDataRefresh` (was `semanticTokensRefresh`). jdtls lists no lenses unless its settings enable them: `javaSettings` turns on `referencesCodeLens` and `implementationsCodeLens` (old boolean) / `implementationCodeLens: "all"` (newer); its lenses come without a command and resolve to the client commands `java.show.references` / `java.show.implementations` with `[uri, position, locations]`. kotlin-lsp (263) answers `null` unless started with `initializationOptions.runMainCodeLens: true` (found in its `InitializeOptions`); then it lists `$(play) Run` / `$(debug) Debug` over main functions with `intellij.jvm.runMain {mainClass, uri, noDebug}`. The editor and MainWindow side is in [editor.md](editor.md#code-lenses).

**Server status**: progress is kept per operation (`Server::progress`: token → title, text, percent, `order` of the last change) for `$/progress` (begin / report / end; a report without a message or percentage keeps the last one) and jdtls' `language/progressReport` (task mapped to "Syncing Gradle project" / "Indexing" …, `subTask` / `status` as the text unless it is a bare "0%", `workDone / totalWork` as the percentage except for indexing, whose total keeps growing). `updateProgressState` fills `ServerState::progress` (the newest), `percent` and `operations` (all, newest first; a percentage is not appended when the text already has one, as jdtls's "Initialize Workspace — 0%" does). The status-bar button shows the server of the current file first (`serverIdFor`, also re-evaluated on `EditorManager::currentChanged`), also while it is starting, and lists every running operation of every server in its tooltip; `m_lspProgress`, a thin `QProgressBar` beside it, is filled to the percentage or runs busy (range 0–0) when there is none. Each server's submenu lists the operations under the status. **Show Server Log** works while starting or running and also after the process ended: `stopServer` / `onServerStopped` keep its lines in `Server::lastLog`, which `logOf` returns while no client exists, so a crashed server still shows why.

## LSP responsiveness (typing lag on Kotlin/Compose, found by measuring)

`LspClient` writes `[qode]` timing lines into the server log (Show Server Log): per request the server round trip, how long our callback blocked the UI, JSON parse time, bytes and how many requests were already waiting (logged for completion always, others when ≥100 ms server / ≥15 ms UI); `LspManager`'s 20 ms watchdog timer adds `UI thread was blocked for N ms` (≥80 ms). Use them first when someone reports lag. Findings: the 200 ms freezes were `LspManager::servers()` running `LspServers::locate` (disk search of PATH/nvm/JDK folders) for every non-running server on each status change → results are cached 10 s (`m_locateCache`) and `servers(false)` (used by `MainWindow::updateLspStatus`) never searches; the status button only restyles when its colour changes.

**Typing-first queue**: `LspClient::request` holds background requests (inlayHint, semanticTokens, documentSymbol, foldingRange, documentHighlight, diagnostic, documentColor, documentLink) in `m_deferred` while an interactive one (completion, completionItem/resolve, signatureHelp) is pending; a held request replaces an older one for the same method + document (the old callback gets error -32800 "superseded", so callers must treat any error as "ignore"), they go out when the interactive answer arrives, with a 1.5 s safety flush. `LspManager::completion` first sends pending didChange (`flushChanges(false)`, no diagnostics pull; `Tracked::pullDue` makes the next timer flush pull). Completion trigger timer is 25 ms; a re-ask for an `isIncomplete` list (kind 3) waits 250 ms for a typing pause while the popup keeps filtering locally.

**Ranking**: `CompletionPopup` sorts by match class, then deprecated last, then *named arguments* (label ends with `=`, i.e. the parameters of the call being typed) first, then the server's `sortText`. A worker thread for JSON parsing was considered and rejected: parse time was ~0 ms. `MainWindow` has `m_dying` because editors are deleted after MainWindow's members, so `destroyed()` slots on editors must not touch members (it caused a crash on Ctrl+Q).

## Linux and Windows

Every OS difference goes through `src/platform/` (see app.md); test a change on both, or say which OS was not tried.
- **Paths and URIs:** servers send `file:///c%3A/...` on Windows. Use `Platform::uriToPath` / `pathToUri`, and compare paths with `samePath` / `isUnder`, never `==` (Windows ignores case).
- **Starting servers:** launchers that may be `.bat` / `.cmd` (`kotlin-lsp.cmd`, `jdtls.bat`, `node_modules\.bin\*.cmd`, `npm.cmd`) go through `Platform::setCommand`. Short-lived tools started that way are stopped with `Platform::killTree`, otherwise java / node keep running after cmd exits. Read their output with `decodeOutput`.
- **Kotlin LSP:** `kotlin-server-<v>.tar.gz` (one top folder) on Linux, `kotlin-server-<v>.win.zip` (no top folder, `bin\intellij-server.exe`) on Windows. Each has its own pinned SHA-256 in `LspInstaller.cpp`. JetBrains builds expire: when the pin stops starting, bump `kPinnedVersion` and both hashes.
- **jdtls:** `config_linux` / `config_linux_arm` vs `config_win` (no ARM build on Windows).
- **Installs:** archives are unpacked with `Platform::setUnpackCommand` (System32 `tar.exe` on Windows). `current` is a symlink on Linux and a junction on Windows (`setCurrentVersion` / `currentVersion`). `~/.local/bin/<name>` is a symlink on Linux and a `.cmd` file on Windows (`writeCommandLink`). Delete only with `Platform::removeTree`: Qt's `removeRecursively` follows junctions.
- **Finding servers:** `Platform::languageServerDirs` (LLVM, MSYS2) and `extraBinDirs` (npm, pnpm, WinGet, Volta, Scoop) add Windows install folders. Both return nothing on Linux.
- **Removing:** the remove dialog runs `rm` on Linux and `rmdir /s /q` / `del /f /q` on Windows (`setRemoveCommand`). For clangd on Windows it suggests winget / MSYS2 pacman depending on where `clangd.exe` lives.
