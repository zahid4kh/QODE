# Python

## python

language server and packages.

**Server**: spec ids `python` (basedpyright: `basedpyright-langserver --stdio`, `wantsConfiguration`) and `ruff` (companion, `ruff server`, `languageIds` py→python), both `Installer::Pip` with `managedId` "python", i.e. one private venv `~/.local/share/QODE-AGENTIC/lsp/python` made by `lsp/PipInstaller` (uv when `LspServers::uvExecutable()` finds it — `uv venv` + `uv pip install` — else `python3 -m venv` + `pip install`; a failed uv run is retried once with pip; a venv it created itself is deleted again on failure/cancel; Debian's missing `python3-venv`, offline and externally-managed errors get friendly messages) with `dialogs/PipInstallDialog` (copy of the npm dialog) and `LspRemoveDialog::buildPip` (`rm -rf` of that folder). basedpyright needs no Node (it ships `nodejs-wheel-binaries`, ~300 MB total). `configurationFor` (LspManager.cpp) answers its `workspace/configuration` requests (sections `python` and `basedpyright`): `pythonPath` = the project venv's interpreter (`PythonEnv::venvPython(root, activeVenv(root))`), nothing is written into the project, `typeCheckingMode: standard` (basedpyright's own default is the noisy "recommended"), `disableOrganizeImports` (Ruff does that). basedpyright pushes diagnostics, ruff uses pull diagnostics (generic path). `LspManager::formatting` asks every ready server of a file (main first, then companions) so Ruff formats Python through LSP, and `Formatter` has a `ruff format` tool (before black) that also finds the managed copy.

**Environment**: `project/PythonEnv` (`findVenvs`, `activeVenv` = the project's chosen `SettingsManager::pythonVenv` else `findVenv`, `venvPython`, `venvVersion` from pyvenv.cfg); terminal activation, the language server and the package dialog all use `activeVenv`.

**Packages**: `python/PythonTools` (Qt Core only: the uv/pip command lines for create/install/uninstall/list, `splitRequirements` validates the install field, `packageForModule` maps `yaml`→`pyyaml` etc.) and `python/PackageManager` (runs them against the environment's own `bin/python`, so no shell activation is needed and system Python is never touched; one change at a time, listing on a separate process: `list` then `list --outdated`; uv when installed, else pip). `dialogs/PackagesDialog` (modeless, styled from `Theme`) lists packages with filter / "updates available", installs typed names or a requirements.txt / pyproject.toml (`-e`), upgrades and uninstalls selections, shows the live log, picks between several venvs and, in a project without one, offers to create `.venv`. `MainWindow::m_pythonPkgAct` (package icon) sits next to Run / Run Configuration in the main toolbar and is visible only while `PythonEnv::activeVenv` is non-empty (`updatePythonUi`, re-evaluated on project open/close and every 3 s by `m_venvTimer` so a venv made in the terminal shows up); View > Tool Panels > Python Packages… is always available. After packages or the environment change `restartPythonServer` restarts basedpyright so imports resolve. Alt+Enter on an unresolved import (`reportMissingImports` / `reportMissingModuleSource`, `unresolvedPythonImports`) adds "Install “pkg” in the virtual environment…" which opens the dialog and runs `PackagesDialog::installNow`. A venv created from the dialog offers to activate it in the terminal.

## Linux and Windows

- **venvs:** `bin/python` on Linux, `Scripts\python.exe` on Windows. Use `Platform::venvBinDir` / `venvProgram`.
- **Interpreter:** `Platform::pythonInterpreter` gives `python3` on Linux. On Windows it asks `py -3` first and never uses the `WindowsApps\python.exe` Store stub, which opens the Store instead of running.
- **pip:** always `python -m pip`. Read output with `Platform::decodeOutput`.
