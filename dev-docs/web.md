# Web dev server and Expo

## webdev

dev server for JS/TS projects. `WebProject::detect(root)` reads `package.json` (scripts `dev`/`develop`/`start`/`serve`/`preview`, best first), the package manager from the lockfile (`bun.lock[b]` → bun, `pnpm-lock.yaml`, `yarn.lock`, `package-lock.json`, else the `packageManager` field, else npm) and the framework from dependencies (default port + port flag), and builds `bun dev` / `pnpm dev` / `yarn dev` / `npm run dev` (a fixed port appends the framework's flag, `npm` needs `--`). `DevServer` runs it via `/bin/sh -c` in its own session (`setsid`, so stop = `kill(-pid)` SIGTERM then SIGKILL after 4 s), strips ANSI, and reads the port from the printed `localhost:NNNN` / "listening on …" line: Starting (amber) → Running (green, port shown) / Failed (red); it also exports `$PORT`, adds Node's folder to PATH and sets `PYTHONUNBUFFERED=1` (Python block-buffers stdout into a pipe, so `python3 -m http.server` never showed its port line and stayed Starting). `starts()` counts the starts (a restart too), which the chat's server tools wait on ([agent.md](agent.md)). `DevServerBar` is the toolbar strip (dot + clickable address, start/stop, restart, log, settings; `ServerDialogs`: `ServerConfigDialog`, modeless `ServerLogDialog`); it re-detects when `package.json`/lockfiles change and emits `availabilityChanged`, upon which `MainWindow::updateRunToolbar` swaps the Run File / Run Configuration buttons for the bar. In a web project F5 starts/restarts the server (unless that file type has its own run command) and Run Configuration opens the server settings. Per-project overrides (`manager`, `script`, `port`, `command`) live under `webServer` in the project JSON (`SettingsManager::webServer`). The server is stopped on project close/switch and app exit.

**Nested projects**: when the root has no server script, `WebProject::findNested` (two levels, skips node_modules/dist/…) finds e.g. `docs/`; `DevServerBar::nestedProjectsFound` → `MainWindow::askNestedWebProject` asks "Run Server / Not Now / Don't Ask Again" (`webServer.declined`), accepting stores `webServer.dir` (relative) which becomes `DevServerBar::workDir()` (server cwd, `.env` folder, watcher); the settings dialog has a folder picker.

**Hardcoded ports**: a script that pins its port (`-p 4000`, `--port=…`, `PORT=…`; `WebProject::scriptPorts`) never gets QODE's port flag/`$PORT`; ports in vite/nuxt/astro configs or `.env` are only reported (`configPort`), and the actual port always comes from the server output.

**Live preview**: `WebPreview` is a right-island panel (`MainWindow::toggleWebPreview`, the globe button in `DevServerBar`, the agent's `show_panel web_preview`) showing the dev server's page in Qt WebEngine. It is optional at build time (`qtHaveModule(webenginewidgets)` and not `CONFIG+=no_webengine` → `QODE_HAS_WEBENGINE`). A build without it has no preview at all: `DevServerBar`'s globe and `ExpoBar`'s phone button are hidden, the Expo menu has no Preview in Phone Mockup, `toggleWebPreview` / `showPreviewTarget` do nothing (so a starting server does not open it either), and the chat's `show_panel web_preview` and the `preview` tool group are off; the dev servers themselves still run and their page opens in the browser, and `main.cpp` sets `Qt::AA_ShareOpenGLContexts` before the application exists, as WebEngine requires. It follows `DevServer::stateChanged`: placeholder with Start / Show Log while stopped, starting or failed, the page once Running (a server that starts opens the panel unless another right panel is open). Chromium is only created when the panel is first shown with a running server (`m_pendingLoad`). A restart on the same port returns to the route that was open. The view uses its own `QWebEngineProfile` ("preview": cookies/localStorage in `~/.local/share/QODE-AGENTIC/web-preview`, HTTP cache in memory only so dev files are never stale); pages must be deleted before that profile (see the destructor). Device modes lay the page out at the device's CSS size and zoom it down so the whole device fits, centred (desktop only fits the width); Fit is the panel's own width. Phone shows the page in a mockup from `resources/phone-mockup/`, picked with the iOS / Android `SegmentPill` above it: iPhone 15 (PNG, 393 × 852) or Pixel 9 Pro (SVG, 412 × 915). `Mockup` holds each file's screen rectangle, corner radius, body outline and camera in the file's own units; both files have an opaque black screen, so the page is laid over it. The SVG punches its screen out with a `<mask>`, which Qt's SVG renderer draws as plain shapes (a white sheet behind the phone), so `renderMockup` strips the mask before rendering through the `svg` image plugin. Tablet (820 × 1180) is a frame drawn in theme colours, desktop (1440) a thin outline. `DeviceStage` composes backdrop, shadow and device into one `scene` pixmap; five `DevicePatch` widgets above the page copy pieces of that scene back over it (the screen's four rounded corners and the Dynamic Island / punch hole), antialiased and letting the mouse through. They copy the whole scene, not just the device, because a screen's square corner reaches past the phone's rounder outline. Phone / tablet can be turned sideways and hide the page's scrollbars with an injected `::-webkit-scrollbar` style (a `qode-device` page script for later loads plus `runJavaScript` for the open page, in the application world); the same style lets React Native Web's single-line text in a `[role=tablist]` overflow its box by a few pixels (`overflow: clip` + `overflow-clip-margin`), since React Navigation's bottom tabs leave a label under the icon only 10px and the web build clipped the bottom of the letters where iOS draws past the frame. An Expo app in the upright phone gets the mockup's safe-area insets (iPhone 15: 59 top / 34 bottom, Pixel 9 Pro: 52 / 24): a browser reports `env(safe-area-inset-*)` as 0 and a page cannot change it, so `kSafeAreaJs` (a `qode-safe-area` script at document creation, main world) wraps `getComputedStyle` to answer for inline styles that use `env()` as if it held those values. react-native-safe-area-context's web provider measures exactly such an element; switching iOS / Android updates the values and fires the transition event it listens to, so it re-measures without a reload. `PreviewPage` collects console messages (`console()`, shown in the strip toggled by the status-bar button; cleared on each load) and sends off-site links and new tabs (`target="_blank"`, a plain `window.open`) to the system browser. A sized popup (`window.open` with features → `WebDialog`, which is how Firebase `signInWithPopup` / Google / OAuth sign-in opens) instead opens in a top-level `QWebEngineView` on the same profile: the opener waits for it through `window.opener` / `postMessage` and polls `closed`, and the session cookie must land in the preview's profile, so a popup handed to Brave/Chrome signed in there and the preview never heard back. The popup closes on `windowCloseRequested`; `PreviewPage` deletes any still open in its destructor (before the profile). Leave the user agent alone: with the `QtWebEngine/x.y` token removed it claims to be Chrome while client hints name only "Chromium", and Google answers that mismatch with "Couldn't sign you in — this browser or app may not be secure" (`/signin/rejected`) right after the email; the stock agent gets through (checked against accounts.google.com with Qt 6.11 / Chromium 140). DevTools open in a separate window. The engine's Chromium version is the installed Qt's (Qt 6.4 = Chromium 102; Tailwind ≥ 4.1 ships `@supports` fallbacks for `oklch`/`color-mix`, so such pages render, but CSS newer than Chrome 102 such as `:has()`, container queries, nesting or `dvh` does not). `build-deb.sh` (system Qt 6.4) picks up the WebEngine dependency through `dpkg-shlibdeps`; `build-deb-qt.sh` (package `qode-bundled`) bundles `QtWebEngineProcess`, its `resources/` and locales from the Qt it builds with (6.11), located through `qt.conf`; `build-deb-qt-noweb.sh` (`qode-bundled-noweb`) builds with `CONFIG+=no_webengine` and leaves Chromium out. The chat's preview tools use its public helpers (`capturePage`, `evaluate`, `setDeviceMode`, `cssViewport`, `loadsFinished`, console serials); see [agent.md](agent.md).

**Preview targets**: the panel shows one `WebPreview::Target` at a time, built by `MainWindow::updatePreviewTargets`: `web` (the `DevServerBar` server, named after the framework) and `expo:<rel>` for every Expo app. With more than one, the header has a target menu and, while the chosen target is stopped, the placeholder lists a Run / Show button per target ("Show" when its server already runs, so it is not restarted). The choice is kept in the project's `expo.preview`. An Expo target is phone only: the Fit / Tablet / Desktop / rotate buttons are hidden and the web app's device and orientation come back when switching away. Switching loads `about:blank` (the other app stops polling and hot-reloading) and remembers each target's last route. The globe button picks `web`, the Expo bar's phone button the current Expo app (and starts it). A web app next to an Expo app at the root (SlowJourney: Expo root, Next.js `docs/`) is offered through the nested-project question, which runs whenever the root itself is not an available web server.

**`.env` editor**: `EnvDialog` (key icon in the bar) edits `.env*` in the work dir as a table; saving rewrites only changed/added/removed entries (comments, blank lines, `export` prefixes and untouched lines stay byte-identical), quoting values only when needed, and can restart the running server.

## expo

React Native Expo support; QODE shows nothing React-Native-specific unless `ExpoProject::detect(root)` (Qt Core) finds a folder whose package.json depends on `expo` (root plus three levels, skipping node_modules/ios/android/build output, so monorepo apps such as `apps/mobile` are found; plain React Native without `expo` is ignored). `ExpoApp` carries the app.json / app.config path and the SDK (installed `node_modules/expo` version, hoisted ones included, else the declared range → `54.0.0`). `ExpoBar` (toolbar widget, replaces the Run File / Run Configuration buttons like `DevServerBar` does): Run button (click = last used configuration, F5 via `MainWindow::runCurrentFile` when the file is in an app). A separate chevron button `m_runMenu` sits beside it, and right-clicking Run opens the same list; `QToolButton::MenuButtonPopup` was dropped because its arrow part was a thin strip, ugly at any zoom. The list has Run on Android / iOS (disabled off macOS) / Start Metro / Prebuild Android / Prebuild iOS (all `npx expo …`, typed into the terminal as `(cd '<app dir>' && …)` through `MainWindow::runExpoCommand`), Open React Native DevTools (sends `j` to the current terminal pane via `TerminalPanel::sendInput`, only after Metro was started from the bar), an app picker for monorepos (`SettingsManager::expo()` = `{dir, last}`), Configure app.json and Expo Schema Cache. `DevServerBar::setIgnoredDirs` keeps `expo start` apps from also showing up as web servers (and from the nested-web-project prompt). **Web preview**: `ExpoWebServer` (a `DevServer` owned by `ExpoBar`, one for all apps) runs `npx expo start --port <first free from 19006>` headless in the app folder, so a Metro in the terminal keeps 8081. No `--web`: that opens a browser and may install packages, and Metro serves web on its port anyway. Not a TTY, so the CLI is non-interactive; `CI` is not set because it turns off reloads. An app needs `react-native-web` and `react-dom` installed (`ExpoApp::web`, hoisted ones count); otherwise the preview offers **Add Web Support** (`npx expo install react-native-web react-dom @expo/metro-runtime` in the terminal). `web.output: "static"` (the template default) makes Metro render every route in Node on each page load, and app code that touches `window` or a native module at import time (RevenueCat, sqlite...) then crashes Metro or serves an error page. The preview only needs the app in the browser, so `resources/expo/web-preview.cjs`, copied to `~/.cache/QODE-AGENTIC/expo/` and loaded with `NODE_OPTIONS --require`, wraps `@expo/config`'s `getConfig` (a `Proxy`, its CommonJS exports are getters) and turns `static` into `single`; app.json is never touched and `server` (API routes) is left alone. Metro only reports a failed bundle in its own output (the browser gets an empty page): `ExpoWebServer::scan` takes the line after "Bundling failed" and emits `DevServer::buildError`, which the preview adds to its console and opens. A line starting with `…Error` becomes the error shown when Metro exits. The preload also: defaults babel-preset-expo's `unstable_transformImportMeta` to true (wraps the preset function when Babel loads it in Metro's workers, which inherit `NODE_OPTIONS`), because packages whose browser build reads `import.meta` (zustand 5's middleware) stop the web bundle with "Cannot use 'import.meta' outside a module" while a device gets their React Native build; appends `qode-web-preview` to Metro's `cacheVersion` (wrapping `@expo/metro-config`'s `getDefaultConfig`) so transforms cached without that option are not reused; and, when the app resolves `expo-sqlite`, adds `wasm` to `assetExts` and sends `Cross-Origin-Opener-Policy: same-origin` / `Cross-Origin-Embedder-Policy: credentialless` on every response (patching `http.ServerResponse.writeHead`: Expo serves the HTML from its own middleware, ahead of `enhanceMiddleware`), which Expo's docs otherwise have the app put in metro.config.js. PushUpBro runs this way in a current Chromium without changes; under Qt 6.4 expo-sqlite still fails, its OPFS worker needs synchronous access handles (Chromium 108), so a target whose app depends on expo-sqlite carries `minChromium = 108` and the preview says so when the page loads (`qWebEngineChromiumVersion()`), offering Open in Browser.

**The preview is the app's web version, and says so**: everything Expo-specific in the panel words it as react-native-web in a phone frame, not the native build. The status line adds "web version" (its tooltip explains that native-only modules don't exist there); the no-web-support placeholder says the app is set up for iOS / Android only, that Add Web Support changes package.json and that device-only code may still stop on start-up. Errors inside the app (a native module without a web version) show in Expo's own overlay; on top, `PreviewPage`'s console hook watches for an uncaught error ("Uncaught …" or React's "An error occurred in the <X> component") and 1.5 s later checks whether `#root` is still empty (text plus img/svg/canvas/input/video; Expo's overlay lives outside the root). If so a notice above the page names the error and explains that this is the web build, not a broken app, with Open in Browser and Console; for a web target it only names the error. It hides on the next load.

**Routes**: for an app with `expo-router` in package.json, `ExpoRoutes` (Qt Core) lists the screens from the routes folder (the expo-router plugin's `root` in app.json, else `src/app` before `app`, as Expo Router decides): groups `(tabs)` dropped, a trailing `index` collapsed, `_layout` / `+html` / `+not-found` / `+api` / other `_` and `+` files skipped, `.web` / `.native` suffixes folded into the base route (`.ios` / `.android` skipped), `[id]`, `[...rest]` and `[[...rest]]` kept as written. The target hands a `routes` callback to the preview, read again each time the list opens, so new screens show up without a watcher. The route button next to the address bar lists them (a folder with several screens becomes a submenu; the open route is checked by matching the URL against the pattern), and the address bar completes them (`QCompleter`, substring match). A route with brackets asks for each value (`QInputDialog`, the last value per name is offered again; catch-alls take `a/b/c`) and loads the URL; the app's own guards still run, so a screen behind a login redirects to it until you sign in inside the preview (its profile keeps logins). Bypassing guards was rejected: the apps use `<Redirect>`, `Stack.Protected` and `router.replace` in effects, and the screens behind them read the signed-in user anyway. React Navigation apps declare screens in code, so they get no list. Tested with SDK 54 and 57 under Qt 6.4 / Chromium 102. **app.json editor**: `ExpoConfigDialog` (modeless form: General page for plain values, one page per object/array key, nested cards, type combo per value, add/rename/retype/remove, "New section…"; tooltips, name completion and enum choices from the schema) edits through `expo/JsonDoc`, an order-preserving JSON model (QJsonObject sorts keys) so a save changes only what was edited and keeps key order, indentation and number text.

**Schema**: `ExpoSchema` downloads `https://exp.host/--/api/v2/project/configuration/schema/<sdk>` once, wraps it into `{"expo": {...}}` and caches it in `~/.cache/QODE-AGENTIC/expo/schema-<sdk>.json` (refreshed silently after 30 days; offline falls back to the newest cached one); `MainWindow::pushExpoSchemas` hands it to the JSON language server as `json.schemas` (`LspManager::setJsonSchemas`, sent with `workspace/didChangeConfiguration` when the server is ready and on change) matched on each app's app.json URI. The Expo menu's **Expo Schema Cache…** shows the folder, size and `rm -rf` command and can delete it.

## Linux and Windows

- **Dev server:** the command line goes through `Platform::setShellCommand` (`/bin/sh -c` on Linux; on Windows it is translated to cmd by `ShellSyntax`). The process is tracked with `ProcessTree::track` and stopped with `ProcessTree::stop` / `kill`: a process group on Linux, a Job Object on Windows (it also answers cmd's "Terminate batch job"). Never use `::kill`.
- **npm / npx** are `.cmd` files on Windows: start them through `Platform::setCommand`. `Platform::extraBinDirs` adds the Windows Node install folders to the search.
- **Expo:** the `(cd … && npx expo …)` lines run unchanged in PowerShell and cmd. iOS stays off outside macOS. Expo finds the Android SDK itself.
- WebEngine is optional on both OSes (`noweb` builds): code that uses it stays behind `QODE_HAS_WEBENGINE`.
